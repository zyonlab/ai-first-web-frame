概念

分层与边界

三层，一个方向，由配置强制而不是由 code review 强制。

规则是声明式的

{
  "tags": {
    "packages/*":  ["layer:framework"],
    "domains/*":   ["layer:domain"],
    "apps/*":      ["layer:product"],
    "fragments/*": ["layer:product"]
  },
  "depConstraints": [
    { "sourceTag": "layer:framework", "onlyDependOnLibsWithTags": ["layer:framework"] },
    { "sourceTag": "layer:domain",    "onlyDependOnLibsWithTags": ["layer:domain", "layer:framework"] },
    { "sourceTag": "layer:product",   "onlyDependOnLibsWithTags": ["*"] }
  ]
}

仿 @nx/enforce-module-boundaries。违规是 audit:deps 的 layer-constraint-violation。修正 import，或者故意地修改约束 —— 但不要加个 tag 来躲开它。

为什么框架层不能 import domain

@mvp/contracts 属于框架层。如果业务词汇可以落进去，那么「给请求上下文加一个 A/B 分桶」就意味着修改一个框架包 —— 而每个消费方都会继承你这个产品的名词。

这个压力是真实存在的，所以这里有一个设计好的逃生口，而不是一条被人悄悄违反的规则：ctx.extensions（经校验的字符串 record，以 x-mvp-ctx-<name> 传播）可以容纳这个维度，而不必加宽 schema。domain-code-in-framework-package 是抓另一条路径的审计规则。

同级隔离

还有两条规则挡住 monorepo 天然诱发的横向泄漏：

  • page-importing-another-page / cross-page-import —— 页面应用是独立的可部署物，一个 import 另一个的内部实现，会悄悄把两条发布节奏绑在一起。
  • fragment-importing-page-code —— 伸手去够页面的片段已经不再可独立部署，无论 manifest 怎么写。

服务端 / 客户端

另一个审计（audit:boundary）覆盖分层规则看不见的那个方向：

规则码含义
server-imports-client-module服务端文件拉进了一个 "use client" 模块
server-browser-global服务端文件碰了 document / window / localStorage
page-use-client页面组件被标了 "use client" 但其实不必
large-client-component建议性（warn）的客户端组件体积参考线

audit:deps 另加一条 server-safe-browser-global：packages/* 里的文件在没有 "use client" 的情况下碰浏览器全局对象即失败。这正是 @mvp/runtime/live（本质上只跑在浏览器里）要做成一个带 "use client" 的独立导出子路径、而不是硬塞进主入口的原因。

片段之间怎么共享代码

片段通过发布导出子路径共享代码，而不是去 import 同级片段：

子路径用途例子
./patch纯粹的「帧 → 补丁」逻辑，不碰 DOM@mvp/fragment-order-book/patch
./live浏览器实时面板@mvp/fragment-order-book/live
./islandReact 岛屿组件@mvp/fragment-order-form/island
./manifest给需要它的消费方的 manifest@mvp/fragment-market-header/manifest
./render渲染函数，供组合测试使用@mvp/fragment-order-form/render

纯逻辑放 ./patch、DOM 放 ./live、React 放 ./island —— 这个切分正是让片段的 JS 预算保持诚实的原因，因为页面可以只拉纯粹的那一半而不把 React 拖进来。
