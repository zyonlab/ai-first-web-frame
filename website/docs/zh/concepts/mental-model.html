概念

心智模型

四个想法。这四条立住了，其余 API 读起来就是顺理成章的。

1 · 页面是服务的组合，不是构建产物

页面应用拥有布局和槽位名，但不拥有那些区块。每个区块是一个可以在页面照常运行时被重新部署的 HTTP 服务，因为页面在每次请求时才从注册表解析 serviceUrl 和版本。

实务后果：「给盘口发一个改动」意味着构建一个镜像、注册一个版本、晋级一个通道。它不意味着重建交易页面。

2 · 声明，和它描述的那个东西放在一起

片段在自己的 src/manifest.ts 里声明自己的版本、降级内容、资源、预算、后端代理目标、SSR 数据依赖和浏览器订阅，并由 GET /manifest 发布。

页面只声明它独有的知识：有哪些槽位、每个由哪个片段和哪个通道填充、每槽位超时和缓存策略，以及参数值（当前是哪个币对）。

每当这两份清单对「谁拥有某个事实」产生分歧时，片段赢。这正是让独立部署成真的东西：实时订阅那次重构把约 470 行从交易页面搬进三个片段，回报是改变一个片段订阅什么，现在完全不需要动页面。

3 · 失败是局部的，而且是声明过的

每条边界都有一个声明好的降级形态。槽位有 manifest.fallback。依赖失败会把下游槽位标为 skipped-dependency 而不是去尝试它们。快照不匹配的岛屿不会被水合，留下有效的服务端渲染标记。

唯一会改变 HTTP 状态码的失败，是必需槽位失败，网关把它变成 503。其余一切都是「200，但页面上东西少了」。

这套系统里没有任何一处，会用「产出一个半成品」来回应「某个部件坏了」。这正是版本握手存在的意义。

4 · 重要的东西，都由一条命令检查

本仓库的立场是：没人能运行的约定就是注释。所以：

  • 边界是 Zod schema，其中 6 份还额外导出 JSON Schema；
  • 分层是一份被审计强制的声明式配置；
  • 「片段能独立部署」就是 pnpm verify:unit；
  • manifest 与代码的漂移在结构上不可能发生（代码生成）并且还被检查（verify:manifest-gen）；
  • 文档示例会被执行（docs:test）。

推论，也是已知缺陷作为一等公民页面存在的原因：凡是声明了但没有被检查的东西，都应当按「愿景」对待。11 个性能预算字段里有 5 个属于这一类。
