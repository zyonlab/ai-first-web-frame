概念

最小部署单元

主张是「片段能独立出货」。这一页讲的是什么让它可被检验，而不只是一句架构描述。

这条主张的可执行形式

pnpm verify:unit --name order-book

它按顺序做这些事：

  1. 只构建该单元的依赖闭包 —— pnpm --filter @mvp/fragment-order-book... build → dist/server.js；
  2. 启动构建产物（不是源码）；
  3. 断言 /health、/ready 和 /manifest 报告同一个 manifest 版本；
  4. 断言 POST /render 支撑的输出携带该版本；
  5. 检查该单元的注册表通道。

输出 JSON 信封；每一步都过才 exit 0。Flag：--name、--port、--filter、--skip-build。状态：ok · passed · skipped · failed。

第 3 步是承重的那一步。如果 /health 报的是一个写死的字符串，一次发布就无法知道是哪个构建在应答，「先部署再晋级」就从流程变成了信仰。

打包形式

每个片段一个 Dockerfile，fragments/<name>/Dockerfile，带 EXPOSE <port>。任何镜像仓库或编排系统都能构建并运行它。部署本身刻意没有在这里实现 —— 每个组织都已经有一套。

不重建页面就上线

构建镜像  →  register-fragment --channel canary  →  核对 /health 版本  →  promote-fragment

页面每次请求都从 registry/registry.data.json 解析 serviceUrl 和版本，所以没有任何页面产物发生变化。<FRAGMENT_NAME>_URL 甚至可以在不写注册表的情况下于运行时改变指向。

rollback-fragment 恢复到晋级时记录的版本。

「独立」到底覆盖了什么、没覆盖什么

覆盖了

服务端标记、数据访问、CSS、降级内容、预算、后端代理目标、SSR 数据依赖、浏览器订阅，以及它们所发布的版本。全部在片段里，全部经注册表和 GET /manifest 到达页面。

没覆盖 —— 这是诚实的边界

见下面四条。把它们当成已知边界，而不是待发现的意外。

  • 客户端代码必须被页面静态 import。React 岛屿要注册进页面的岛屿注册表；实时面板要列进页面的面板数组。这里没有运行时模块加载，所以新增一个可交互片段是两行页面改动。改变一个已有片段做什么 —— 包括它订阅什么 —— 则不需要。
  • 岛屿资源不跟随环境变量覆盖。<FRAGMENT>_URL 移动 serviceUrl 和 manifestUrl，但不移动 assetsUrl（F2）。
  • 共享 vendor 属于页面。片段的 jsBytes 以 react/@mvp/* external 的方式计量。两个片段不能各自选择互不兼容的 React 版本；仓库强制单一声明区间。
  • 没有任何东西操练过非 Node 片段。POST /render 契约与语言无关，JSON Schema 也正为此发布，但树里没有非 Node 片段 —— 把多语言当作未经测试，而不是已支持。

计数

22 个可部署单元：1 个网关、7 个页面应用、14 个片段服务。端口 4100、4101–4107、4201–4214，见端口。
