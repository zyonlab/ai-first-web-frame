上手

快速开始

把整套组合跑起来看一眼。比读十页描述快。

全部启动

pnpm install
pnpm dev

pnpm dev 即 pnpm -r --parallel --filter './apps/*' --filter './fragments/*' dev —— 22 个服务一次起。片段服务一两秒内就应答；Next.js 页面应用首次请求时才编译，所以第一次打开某个页面会慢。

地址是什么
http://localhost:4100/网关 —— 浏览器应该只用这个源站
http://localhost:4100/trade/BTC最丰富的页面：9 个槽位、岛屿、实时面板
http://localhost:4100/product/123静态 + ISR + 动态槽位在同一页
http://localhost:4100/manifest/fragments解析后的片段注册表（已应用环境变量覆盖）
http://localhost:4100/manifest/routes路由注册表
http://localhost:4201/某个片段服务自己的首页，带它全部端点的链接

只有 4 个单元有专门的 dev 脚本（dev:shell、dev:page-home、dev:page-product、dev:fragment:promotion-banner、dev:fragment:recommendation-widget）。其余直接用 filter：

pnpm --filter @mvp/page-trade dev
pnpm --filter @mvp/fragment-order-book dev

单独看一个片段

14 个片段提供完全相同的 8 个端点，所以不需要页面就能单独操练一个：

curl -s localhost:4204/health    | jq   # {status,service,version,uptimeMs}
curl -s localhost:4204/manifest  | jq   # manifest 原样返回
curl -s localhost:4204/budget    | jq   # 该单元的性能预算
curl -s localhost:4204/assets    | jq   # manifest.assets

POST /render 收 {ctx, props}，返回 {html, assets, cache, metadata}：

curl -s localhost:4204/render -X POST -H 'content-type: application/json' \
  -d '{"props":{"symbol":"BTC"},"ctx":{"locale":"en-US","tenant":"default"}}' | jq 'del(.html)'
# { "assets": {...}, "cache": {"ttl":0,"tags":["book","book:BTC"]},
#   "metadata": {"name":"order-book","version":"0.1.0"} }

上面那个 ctx 并不是一个完整的 RequestContext —— 完整 schema 还要求 traceId、requestId、featureFlags 和 timestamp。它之所以能work，是因为 parseFragmentRenderRequest 是两层的：先试严格 schema，再回落到宽容信封（ctx 为 partial 且可选），两者都失败才返回 400。

手工戳服务时很方便；但为什么你目前无法知道线上流量是否落在宽容层，见已知缺陷 F14。

4204 是 order-book。完整端口表见端口。

证明一个片段能独立出货

pnpm verify:unit --name order-book

只构建该单元的依赖闭包，启动 dist/server.js，断言 /health、/ready、/manifest 在 manifest 版本上一致，且 POST /render 的输出携带该版本。每一步都过才 exit 0。

读报告

pnpm verify      # 写出 reports/
pnpm reports     # 在 :4300 提供 docs/reports/ —— 关于仓库本身的长篇 HTML 报告
pnpm docs:serve  # 在 :4301 提供这份文档

两个名字很像的目录。仓库根的 reports/ 是机器产物，每次 pnpm verify 重写；docs/reports/ 是手写的长篇分析。它们是刻意分开的。
