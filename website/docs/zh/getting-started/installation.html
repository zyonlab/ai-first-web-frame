上手

安装

没有 bootstrap 步骤。冷克隆之后可以直接 pnpm test。

环境要求

工具版本为什么
Node.js20+@types/node 锁在 20.x；服务本身是纯 Node
pnpm10.13+workspace 协议和仓库里的 lockfile 格式
Docker可选每个片段一个镜像；infra/docker/docker-compose.yml 可跑全部 22 个

只用 pnpm。npm 和 yarn 会生成这个工作区不使用的 lockfile。工具一律通过 pnpm exec <tool> 或 pnpm --filter <pkg> <script> 调用。

安装

pnpm install

就这一步。pnpm test、pnpm verify:manifest-gen 和 pnpm docs:test 都会先跑 scripts/ensure-workspace-build.mts，它委托给 Turborepo，在需要的 dist/ 缺失或过期时构建 packages/ + domains/。

验证这份检出

pnpm verify

14 道闸门，全过则 exit 0，每次运行重写 reports/。Turborepo 缓存热的时候大约半分钟；冷启动几分钟，主要花在 build 上。

某道闸门失败时，排错 · 闸门把每道闸门对应到它写出的报告。

可选：浏览器测试套件

Playwright 用例不属于 pnpm verify，而且它不会启动任何服务。

pnpm exec playwright install chromium   # 一次性，约 94 MB
pnpm dev                                 # 另开一个终端：全部 22 个服务
pnpm e2e

没装浏览器二进制时，纯 API 的用例照常通过，所有浏览器用例都以 Executable doesn't exist 失败 —— 那是少了一个下载，不是产品有问题。

一个值得知道的坑。如果 pnpm build 在 pnpm dev 正在服务时运行，dev server 读的 .next 目录正被构建覆盖，套件会报出毫无意义的结果。在构建前后拿到的 e2e 结果，先重启栈再信。

React 与 Next 版本

React 19.3 配 Next 15.3。全仓库只允许一个声明区间 —— 同一包名出现 peer/dependency 区间分裂会被 audit:deps 判失败。
