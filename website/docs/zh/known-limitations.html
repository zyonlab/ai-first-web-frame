F1 · 优化器在建议把实时盘口静态渲染 — AX，高

reports/optimization-findings.json 当前包含 10 条这种形态的发现：

static-slot-book · 「槽位 book 没有声明依赖，可能不需要动态 SSR。」· recommendation：「若内容是确定的，把槽位策略改成 static、ttl-cache 或 cached-ssr。」

这 10 个槽位包括 book、trades、orderForm、positions、openOrders 和 accountBar —— 全是实时交易面板。照这条建议做会把它们搞坏。

为什么会这样 —— 三环相扣，都可自行复核：

  1. tools/optimization-audit/src/index.ts:55 调用 createOptimizationFindings({ slots, traces })。dataDependencies 根本没有被传进去。
  2. packages/optimizer/src/index.ts:461-468 —— findStaticSlotCandidates 里有一道本该拦住这些的护栏：dependencies.some(d => d.privacy === "user-private" || d.freshness === "realtime" || d.freshness === "client-local")。由于输入永远是 []，这道护栏永远为 false。
  3. packages/optimizer/src/index.ts:470-474 —— 幸存下来的判据是 (slot.strategy ?? "dynamic-ssr") === "dynamic-ssr" && (slot.dependsOn ?? []).length === 0。而 dependsOn 是槽位之间的排序。book 没有 dependsOn 是因为没有别的槽位等它，不是因为它静态。

两者之下是同一个结构性问题：片段确实声明了自己的数据（fragments/order-book/src/manifest.ts:30 → dataDependencies: ["book.l2.<symbol>"]），优化器读的是页面那一侧，而没有任何东西把两边对账。

对 agent 的严重性。这些发现是 info 级，所以闸门通过、人类会一眼扫过去。但一个读 reports/optimization-findings.json 的 agent 看到的是 19 个槽位中 10 个带着结构化的 recommendation 字段，而没有任何信号告诉它这是错的。

修复形态：把片段声明的依赖传进审计输入，并让规则以声明的 freshness 为判据，而不是以 dependsOn。

F2 · <FRAGMENT>_URL 移动服务，却不移动它的岛屿资源 — OPS，中

packages/registry/src/registry.ts 的 withOverride() 从环境变量覆盖改写 serviceUrl 和 manifestUrl，却把 assetsUrl 原样透传。代码自己就写了这一点：

「不相对被覆盖的主机改写 …… 真正的发布需要 assetsUrl 也从同一个覆盖派生，而不只是 serviceUrl。」

所以把一个片段指向另一台主机，它的岛屿 JavaScript 仍然从注册时的地址加载。影响今天唯一带 assetsUrl 的片段：canary 上的 order-form。

由于环境变量覆盖正是「不写注册表也能改指向」的官方路径，这一条削弱了那条路径对任何自带岛屿 bundle 的片段的价值。

F3 · 三个环境变量声明了却无人读取 — 已修复

turbo.json 的 globalPassThroughEnv 里曾列有 REGISTRY_URL、REGISTRY_USERNAME 和 REGISTRY_PASSWORD，而全仓库搜索显示零处读取。它们暗示了一个并不存在的、带鉴权的远程注册表集成，运维完全可能设置它们并期待有效果。

已删除。globalPassThroughEnv 现在是 SHELL_URL、PAGE_*_URL、*_URL、RECENTLY_VIEWED_COOKIE_SECRET —— 全部都有人读。

保留在这一页上，是作为一类腐化的记录：加一条 passthrough 环境变量声明零成本，而它失效时没有任何告警。

F4 · 两个 CLI flag 只存在于代码里 — AX，中

每个生命周期脚本的权威 flag 清单，是它传给 unknownFlagError 的白名单。与操作手册对照：

脚本代码里的 flagCLAUDE.md 里有吗？
mount-slot--depends-on没有
register-fragment--manifest-url没有
register-fragment--assets-url没有

--depends-on 是从 CLI 声明槽位排序的唯一途径，而槽位排序是这个框架的差异化特性之一。一个只读手册的 agent 无从发现它，于是它会转而手改 manifest —— 而同一份手册禁止这么做。

F5 · 网关自己的 HTTP 面没有任何文档 — DX，中

apps/shell-gateway/src/server.ts 提供 /manifest/routes、/manifest/fragments、/_shell/theme 和 /_shell/locale（第 239–252 行）。这四个在 CLAUDE.md 和 docs/ 里一处都没有出现。

/manifest/fragments 尤其重要：它返回应用环境变量覆盖之后的注册表，是排查槽位指向错误最快的工具。它在HTTP 端点里第一次被写下来。

F6 · 晋级路径只在 14 个片段中的 2 个上被操练过 — OPS，中

registry/registry.data.json：只有 promotion-banner（stable + canary）和 recommendation-widget（stable）有 stable 条目。其余 12 个只有 canary，而 page-trade、page-markets、page-portfolio 的每一个槽位挂的都是 channel: "canary"。

两个后果：

  • 被文档化的 canary → stable 生命周期，实际只在 2 个单元上演示过。把晋级和回滚路径当作操练不足来对待。
  • 指向片段所没有的通道的槽位，会静默地解析成降级内容。没有任何构建期检查保证每个槽位的通道在注册表里存在 —— 这本是一道很便宜的闸门，而且正好能抓住这个问题。

recommendation-widget 另外没有 versions 历史，所以 rollback-fragment 因缺少记录目标而正确地拒绝它。

F7 · 七个页面里有两个什么都不组合 — DOCS，低

apps/page-referrals/src/manifest.slots.json 和 apps/page-vaults/src/manifest.slots.json 都是 []。「七个页面组合片段」是夸大：实际是五个页面组合，共 19 个槽位。

因此它们 102 KB 的首屏 JS 是纯框架基线，而预算是 110 KB —— 只有 7.5 KB 余量。给这两个页面加一个岛屿就需要改预算。

F8 · dev:* 脚本只覆盖 22 个单元中的 4 个 — DX，低

根 package.json 有 dev:shell、dev:page-home、dev:page-product、dev:fragment:promotion-banner、dev:fragment:recommendation-widget。没有 dev:page-trade，尽管 page-trade 正是其余一切用来举例的那个九槽位 demo。

pnpm --filter @mvp/page-trade dev 完全可用 —— 这些脚本是个没做完的便利设施，而它们的部分存在反而暗示 filter 写法是兜底而非常规。

F9 · pnpm verify 的 14 道闸门严格串行 — DX，低

scripts/verify.mts:51 —— commands.map(({cmd, args}) => spawnSync(...))。六个审计彼此独立，也独立于 test/build，却没有任何重叠。

这是延迟问题而非正确性问题；热跑约 32 秒，所以很少真的疼。但值得知道，免得有人据此断定这些闸门天生就慢。

F10 · 四个岛屿超标，而没有人认领 — DX，低

reports/server-client-boundary-report.json 里有四条 severity: "warn" 的 large-client-component 未处理：

apps/page-trade/src/hydrate.tsx fragments/chart-panel/src/island.tsx fragments/market-header/src/island.tsx fragments/order-form/src/island.tsx

warn 不会让闸门失败，这条参考线在任何 budget.ts 里都没有数字，也没有单元认领这个告警。它是一盏永久的黄灯：要么给它一个预算字段让它能失败，要么把规则去掉。

F11 · 11 个预算字段里有 5 个哪里都没人管 — DOCS，中

PerformanceBudgetSchema 定义了 11 条上限。真正强制它们的是：

强制方式字段
被 pnpm verify 闸住jsBytes、cssBytes
只被 pnpm verify:runtime 闸住（需要活的 URL，不属于 verify）maxTTFBMs、maxLCPMs、maxCLS
运行时才可测，已被承认rscPayloadBytes
哪里都没人管maxNetworkRequests、maxINPMs、maxFragmentLatencyMs、maxRenderMs、maxMemoryMB

「性能预算是硬闸门：超出 component/fragment/page 预算会让 pnpm verify 失败」这句无限定的表述，只对 11 个字段中的 2 个成立。

对工具公平一点：audit:bundle 对自己的范围是坦白的 —— 报告带 unmeasured 数组逐条说明跳过原因，还有一条 notes 声明运行时指标不在闸门内。缺口在 schema 与闸门之间，以及闸门与那句总结性表述之间。

最尖锐的一例：14 个片段每一个都声明了 maxFragmentLatencyMs 和 maxRenderMs —— 一个片段最具运维意义的两个数字 —— 而没有任何东西读它们。同样地，每个页面都声明 maxINPMs: 200，而运行时闸门实现了 LCP、CLS、TTFB 三项检查，唯独没有 INP。

F12 · 脚手架文件数三处写 9、三处写 11 — 已修复

脚手架实际写 11 个文件（tools/create-component/src/index.ts 的 createFragment）。

写 11（正确）写 9（过期）
CLAUDE.md:48packages/mcp/src/tools.ts:72 —— MCP 工具描述
tools/create-component/AGENT.md:49docs/AI_NATIVE_DEVX.md:215
docs/OPERATIONS.md:27docs/trade-demo/07-deployment-examples.md:56

错的那个数字，恰好在 AI agent 默认唯一会读到的地方：工具列表显示的就是 MCP 工具描述。而 CLAUDE.md 把验收标准写成 files.length === 11，所以一个相信工具描述、断言 9 的 agent，会挂在手册定义正确的那道检查上。

三处过期已全部改成 11。tools/create-component/src/fragmentTemplate.ts:7 仍写 9，刻意不动 —— 那句注释讲的是旧脚手架（曾产出 9 个文件、既不能回答 /render 也构建不出镜像），在上下文里是对的。

保留在这一页上，是因为根因还在：没有任何检查比对「散文里断言的文件数」与「脚手架实际写出的文件数」。脚手架自己的测试也不断言总数，所以下一次偏移会同样静默。

F13 · 交互 ACL 没有被拿去和现实对账 — DX，低

domains/trade-contracts/src/slices.ts:164 把 order-preview 列为 trade.order-draft 的订阅者。而 order-preview 在仓库里别处都不存在 —— 没有片段、没有岛屿、没有 owner id。

没有任何东西校验「声明的发布者或订阅者 id 是否对应一个存在的东西」，所以 ACL 可以和它所治理的系统漂移。对比：实时面板契约由 apps/page-trade/src/liveContract.test.ts 在构建期抓住的，正是同一类漂移。

另有一个不是缺陷但稳定地让人困惑的点：发布者和订阅者 id 是逻辑组件 id，不是片段名。symbol-switcher 是 apps/page-trade/src/hydrate.tsx:173 使用的 owner 身份，不是 fragments/ 下的服务。

F14 · 渲染契约有两层，而层级信号被丢掉了 — OPS，中

parseFragmentRenderRequest（packages/contracts/src/index.ts）先试严格的 FragmentRenderRequestSchema，失败后回落到 FragmentRenderRequestEnvelopeSchema（其中 ctx 为 .partial().optional()），并返回 strict: boolean 说明命中了哪一层。只有两层都失败才返回 ok: false。

已实测：POST /render 带 {"ctx":{"locale":"en-US","tenant":"default"}} —— 一个缺了必填 traceId、requestId、featureFlags 和 timestamp 的上下文 —— 返回 200 和真实 HTML。

两层设计本身是合理的。问题在于 没有任何东西读 strict：全仓库搜索，测试之外没有任何消费方。packages/fragment-host/src/index.ts:209 解构了结果，用了 parsed.ok 和 parsed.request，忽略 parsed.strict —— 没有日志、没有响应头、没有指标标签。

后果：线上你无法知道自己的页面是在发送合法上下文，还是在静默降级到宽容层。这意味着一个悄悄不再传 traceId 的页面，看起来和正常页面一模一样，而它下游的每一条 trace 都在丢失父级。

加一个 counter label 就能修。

F15 · 一个已声明的交互频道对依赖图不可见 — DX，低

tradeSliceContracts 声明了 7 个频道。pnpm graph 报告 6 个 slice 单元。缺的那个是 trade.book-grouping。

tools/release-tools/src/unit-graph.ts:178-184 通过 upsert 各片段 manifest 的 consumes.slices / produces.slices 来建 slice 节点。没有任何 manifest 提到 trade.book-grouping，于是它没有节点也没有边 —— affected 引擎因此无法知道，改动这个频道的载荷会影响 order-book。

与 F1 是同一种形状：两侧各自声明相关的事实，而没有任何闸门去比对。那些 manifest 字段还在 FragmentManifestSchema 之外，所以连拼写都没人校验。

看起来像缺陷，但不是

值得单列，因为下面每一条都会被当成 bug 报上来：

  • 岛屿静默地不水合。那是版本握手在工作。四种明确原因会上报给 onSnapshotMismatch；SSR 标记被刻意原样保留。
  • 没有运行时版本协商。这是刻意的范围取舍，也是 Module Federation 更强的那条主轴。我们检测并拒绝，从不去加载另一个 remote。
  • 页面仍然静态 import 每个岛屿和实时面板。这个仓库没有运行时模块加载。新增一个可交互片段是两行页面改动；改变一个已有片段做什么则不是。
  • /health 和 /ready 返回完全一样的载荷。同一个 handler 提供两者。如果你需要存活与就绪有区别，那是一个待补的缺口，不是一个精妙设计。
  • 页面健康信号是隐藏 div 而不是 <meta>。刻意如此：它是给网关的信号，不是文档元数据。React 19 会把 <meta> 提升进 <head>，而那恰好是降级标记最不该去的地方。
  • reports/ 一直在变。机器产物，每次 pnpm verify 重写。手写的那份在 docs/reports/。

怎么用这一页

如果你在做选型：会改变决策的是 F1、F11 和 F14 —— 一个给出错误建议的工具、一条比实现更宽的表述、一个在主边界上的可观测性空洞。三条都不是设计死胡同，每条大约各一天工作量。

如果你是在这里干活的 agent：照任何优化器建议行动之前先读 F1；断定某个 flag 不存在之前先读 F4。

F3 和 F12 标记为已修复但保留，因为让它们发生的机制还在：passthrough 环境变量失效时没有告警，也没有测试比对文档写的文件数与脚手架实际产出。
