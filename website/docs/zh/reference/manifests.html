清单（Manifest）

三种 manifest，全部经 Zod 校验。

片段 manifest — fragments/<name>/src/manifest.ts

FragmentManifestSchema 的字段：

字段类型说明
namestringkebab-case；与标记里的 data-fragment 对应
versionstring由 /health、/ready、/manifest 报告
ownerstring团队
renderModessr | edge-ssr
renderStrategyRenderStrategy默认 dynamic-ssr
cachePolicy可选{ttl, tags, vary}
fallbackstring失败时替换上去的 HTML
assets{js: string[], css: string[]}
proxyrecord绝对 URL 或 / 开头的路径；默认 {}
subscriptionsstring[]浏览器面板持续订阅的 source id 模板；默认 []
budgetPerformanceBudget必须是 scope: "fragment"

线上的 manifest 还带着 schema 未建模的字段 —— endpoint、dependsOn、dataDependencies、consumes、produces、layoutHint、metadata。GET /manifest 原样返回对象，所以这些字段确实会到达消费方；单元图加载器用 FragmentManifestSchema.passthrough() 校验，所以它们能通过校验而不被剥离。

关于这层校验有两件事要知道：

宿主并不做校验。createFragmentServer 把 manifest 的类型写成 FragmentManifestLike —— 只有 {name, version, assets} —— 并且从不解析它。schema 强制发生在 tools/release-tools/src/load-graph.ts，只在你使用图/affected 工具（pnpm graph、pnpm affected:graph）时才跑，不属于 14 道 pnpm verify 闸门中的任何一道。当前 14 份真实 manifest 全部通过（pnpm graph 能加载 72 个单元）。

那些 passthrough 字段是约定，不是契约。尤其 consumes.slices / produces.slices 喂给单元图的 slice 边，而没有任何东西把它们与权威的频道清单对账 —— 一个没有 manifest 提及的已声明频道，对这张图是不可见的（F15）。

页面 manifest — 槽位

apps/<page>/src/manifest.slots.json 是一个 JSON 数组（不是 {slots: […]}）。每一项：

字段类型说明
namestring槽位 id，页面内唯一
fragmentstring注册表里的名字
channelReleaseChannel可选
strategyRenderStrategy可选
timeoutMsint ≥ 0可选
propsrecord可选
staticHtmlstring可选；strategy: "static" 使用
cachePolicy{ttl, tags, vary}可选
dependsOnstring[]其他槽位名；默认 []
dataDependenciesstring[]页面数据源 id；默认 []
requiredboolean可选；true ⇒ 失败会让页面 unhealthy

reserved: true 出现在 page-product 的 price-panel 槽位上。它不在 PageManifestSchema 里 —— 这是一个约定，把该槽位排除在代码生成之外、保持手工渲染。那个槽位同时指向一个注册表里不存在的片段，所以它从不渲染；这是设计如此，但只能靠读 CLAUDE.md 才能发现。

更外层的页面 manifest（PageManifestSchema）还有 route、renderMode（ssr|ssg|isr|hybrid）、revalidateSeconds、seo: {title, description}、demonstrates（docs/DEMOS.md 由它生成的能力索引）和一个页面级 budget。

生成的运行时形态

每次成功的 mount-slot 都会从该 JSON 重新生成 apps/<page>/src/fragmentSlots.gen.ts（一个 FragmentSlotDefinition[]）。不要编辑它。mount-slot --page <p> --check 校验新鲜度；pnpm verify:manifest-gen 在 pnpm verify 内对所有页面执行。此外每个页面的 manifestSync.test.ts 还会跑 diffManifestAgainstRuntime 作为第二道独立检查。

注册表 — registry/registry.data.json

{ "fragments": { "<name>": {
    "stable":  { "version", "serviceUrl", "manifestUrl", "assetsUrl?" },
    "canary":  { … }, "preview": { … },
    "versions": { "<version>": { … } }
} } }

serviceUrl 必须能解析为 URL。versions 是晋级/回滚历史。registry/releases.json 是只追加的晋级日志。

组件 manifest — @mvp/ui

ComponentManifestSchema = {metadata, budget（scope "component"）, assets}，其中 ComponentMetadataSchema 是 {category, serverSafe, propsSchema, description}。serverSafe 是服务端/客户端边界审计要读的字段。

给非 TypeScript 消费方的 JSON Schema

FragmentManifestJsonSchema、PageManifestJsonSchema、FragmentRegistryJsonSchema、FragmentRenderRequestJsonSchema、FragmentRenderResponseJsonSchema、RequestContextJsonSchema —— 预生成导出（draft-07）。其他导出的 Zod schema 可按需用 toJsonSchema(schema, name?) 转换。
