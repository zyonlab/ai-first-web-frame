HTTP 端点

片段服务 — 8 条路由

14 个片段提供的正是这 8 条，因为它们来自 @mvp/fragment-host 而不是各自的服务代码。

方法路径响应
GET/该服务自身端点的 HTML 索引，外加一次实时示例渲染
GET/health{status:"ok", service, version, uptimeMs}
GET/ready与 /health 完全相同的载荷
GET/metricsPrometheus 文本（PROMETHEUS_CONTENT_TYPE）
GET/manifest片段 manifest，原样返回
GET/assetsmanifest.assets
GET/budget该单元的性能预算
POST/render{html, assets, cache, metadata}

/health 里的 version 是已部署的 manifest 版本 —— 这正是一次发布能在晋级通道之前断言「是哪个构建在应答」的依据。

/health 和 /ready 是同一个 handler。这个宿主里不区分存活与就绪；如果你需要区分，那是一个待补的缺口，不是一个待发现的精妙设计。

POST /render

请求 {ctx, props}。两层校验：严格的 FragmentRenderRequestSchema，然后是 ctx 为 partial 且可选的宽容信封，最后才 400：

{ "error": { "code": "invalid-render-request", "issues": [ … ] } }

响应：

{
  "html": "<style data-fragment-style=\"order-book\">…</style>…",
  "assets": { "js": ["/assets/order-book.client.js"], "css": ["/assets/order-book.css"] },
  "cache":  { "ttl": 0, "tags": ["book", "book:BTC"] },
  "metadata": { "name": "order-book", "version": "0.1.0" }
}

片段可以通过 extraRoutes 增加路由，但上面 8 条是固定的。

网关 — 对外源站

方法路径用途
GET/health网关存活
GET/metricsPrometheus 文本
GET/robots.txt由站点源站生成
GET/sitemap.xml由路由注册表生成
GET/manifest/routes路由注册表，JSON
GET/manifest/fragments解析后的片段注册表（已应用环境变量覆盖）
GET/_shell/theme主题选择端点
GET/_shell/locale语言选择端点
ALL/_fragment/<fragment>/<target>/*片段后端代理
GET/_next/*Next.js 资源透传
GET/*路由解析 → 代理到拥有该路由的页面应用

/manifest/fragments 是排查槽位指向错误最快的工具：它返回的是应用环境变量覆盖之后的注册表，所以它回答的是「这个槽位实际会去调哪个地址」。

超时：SHELL_PAGE_TIMEOUT_MS、SHELL_ASSET_TIMEOUT_MS、SHELL_FRAGMENT_PROXY_TIMEOUT_MS。必需槽位失败时的状态码：SHELL_REQUIRED_FAILURE_STATUS（0 关闭）。
