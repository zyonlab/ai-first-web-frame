简介

这是什么

一个把「一个网页由多个各自独立部署的服务端渲染服务拼成」这件事做成可校验契约而不是团队约定的框架。

它要解决的问题

一个大型产品页面通常由好几个团队共同拥有，却作为一个产物发布。任何一处改动都意味着重建并重新部署整个页面；而其中一块变慢或挂掉，整个页面跟着陪葬。

另一条路是浏览器侧微前端：把组合搬到客户端，代价是 JavaScript 体积和首屏时间。对一个必须被收录、必须首屏快的页面来说，这笔交易是亏的。

这个框架在服务端组合。每一块是一个 HTTP 服务，对 POST /render 返回 HTML；页面并行去取，谁先就绪谁先流式输出，失败的那块用它自己声明的降级内容顶上。

仓库可被 agent 寻址

文档示例由 CI 执行，所以 agent 读到的东西是被证明还能跑的。

1 · 片段是最小部署单位，而且可执行

pnpm verify:unit --name <fragment> 只构建该单元的依赖闭包，启动构建产物，然后断言 /health、/ready、/manifest 报告的 manifest 版本一致，且 POST /render 的输出携带同一版本。每个片段有自己的 Dockerfile。发布新版本不需要重建页面：页面在每次请求时从 registry/registry.data.json 解析 serviceUrl 和版本。

详见最小部署单元。

2 · 每条边界都是 schema，不是约定

packages/contracts/src/index.ts 里的 35 份 Zod schema 覆盖了渲染请求/响应信封、两种 manifest、注册表文件、请求上下文、岛屿快照、性能预算和数据依赖描述符。其中 6 份还额外导出预生成的 JSON Schema，这样非 TypeScript 的消费方也能校验同一套契约。

详见契约优先。

3 · 仓库可被 agent 寻址，而不只是被人阅读

8 个 MCP 工具（packages/mcp/src/tools.ts）暴露了整条生命周期。每个生命周期 CLI 都打印带 status 字段的 JSON 信封，失败时不写任何文件。每个 packages/* 和 domains/* 目录都带一份 AGENT.md，其中的 TypeScript 代码块会被 pnpm verify 里的 pnpm docs:test 真正执行 —— 36 个文件、41 个可执行块 —— 所以一个失效的示例是构建失败，不是待办事项。

详见AI 接入。

它不是什么

这一节比上一节更重要，因为选型错误通常来自高估。

不是客户端微前端运行时。没有运行时模块加载，也没有版本协商。SSR 快照与页面期望版本不匹配的岛屿不会被水合（有四种明确的失配原因），它永远不会从另一个 remote 去加载。需要运行时远程加载，应该用 Module Federation。

不是注册表服务。片段注册表就是仓库里的一个 JSON 文件（registry/registry.data.json），由 CLI 以原子写 + 咨询锁的方式改动。它给你通道、晋级和回滚，但不给你跨仓库分发。

不是部署系统。它产出每个单元一个镜像，以及一个可以按片段在运行时重新指向的注册表。把镜像推上线是你的平台的事。

不是语言无关的。片段是构建在 @mvp/fragment-host 上的 Node 服务。线上格式（POST /render → {html, assets, …}）本身与语言无关，JSON Schema 也正是为此而发布，但仓库里没有任何一个非 Node 片段。把多语言当成「未验证」而不是「已支持」。

一次请求经过什么

  1. 浏览器打到网关（:4100），网关从 @mvp/routes 解析路由并代理到拥有该路由的页面应用。
  2. 页面应用从 src/manifest.slots.json（经由生成的 fragmentSlots.gen.ts）读取槽位，调用 executeFragmentSlots 或 streamFragmentSlots。
  3. 调度器把槽位和数据依赖做拓扑分层，每层并行执行，每个槽位独立超时，依赖失败的槽位直接跳过。
  4. 每个槽位经注册表通道解析到具体片段版本，再发 POST /render。命中缓存策略时则从有界的进程内缓存返回。
  5. 页面渲染一个健康标记；网关把「必需槽位失败」映射为 503。
  6. 浏览器里，只有通过快照握手的岛屿才水合；声明了实时订阅的面板经 @mvp/runtime/live 订阅数据源。

每一步都有对应的指南：页面组合、槽位调度、降级与页面健康、岛屿与水合、实时订阅。
