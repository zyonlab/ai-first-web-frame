槽位调度

这是 Podium 没有对应物的部分：槽位和数据依赖构成同一张有向图，按拓扑分层执行。

两种边

dependsOn — 槽位到槽位

「在 accountBar 之后渲染 orderForm」。当一个槽位的渲染确实需要另一个的结果时才用。

dataDependencies — 槽位到数据

指名页面数据源注册表里必须先解析完的条目。两个槽位指同一个 id 时共享一次解析。

两者都喂给同一个计划器。但都不是关于可缓存性的陈述 —— 一个没有 dependsOn 的槽位并不因此就是静态的，这正是建议性优化器目前犯的错。

不执行也能检视计划

import { createSlotDataExecutionPlan } from "@mvp/runtime";

const plan = createSlotDataExecutionPlan({ slots, dataDependencies });
// plan.levels : ScheduledNode[][]  — 每层并行
// plan.hints  : SchedulerHint[]

在测试或 lint 规则里很有用：在 manifest 出货之前断言计划是你想要的形状。

提示

种类含义
long-serial-chain图里有一条很深的路径，会主导延迟
unnecessary-barrier有东西造成了声明的边并不要求的等待
duplicate-data-resolution同一个数据 id 被解析了不止一次

提示是建议性的：它们出现在 execution.hints 和优化器报告里，不会让构建失败。

执行语义

  1. 每层并行执行；第 n+1 层在第 n 层全部落定后开始。
  2. 每个槽位有自己的超时 —— slot.timeoutMs 或页面默认值。超时后该槽位变成它声明的降级内容，页面其余部分不受影响。
  3. 某节点失败时，它下游的一切不会被尝试，报告 status: "skipped-dependency"，与「尝试过并失败」区分开。
  4. execution.health 汇总：任一必需槽位失败 ⇒ unhealthy；其他失败 ⇒ degraded；否则 ok。

失败永远是局部的。不存在某个槽位的异常中断整个响应的路径。

流式

const { slots, result } = streamFragmentSlots(options);
// slots.<name> : Promise<FragmentRenderResponse>  — 它自己那层落定就 resolve
// result       : Promise<FragmentSlotsExecution>  — 全部落定才 resolve

每个按槽位的 promise 都会 resolve，永不 reject。失败或被跳过的槽位 resolve 成与屏障 API 相同的降级响应，所以 <Suspense> 边界永远不需要 try/catch。

这正是页面可以先 flush 外壳和快槽位、而不必为最慢的那个槽位扣住整个响应的原因。

超时

withTimeout(promise, ms, onTimeout?) 是底层原语。它刻意不建立在 AbortSignal.timeout 之上 —— 后者在某些测试 DOM 环境里不存在，这也是网关的超时辅助函数以 createUpstreamTimeout() 形式单独存在的原因。
