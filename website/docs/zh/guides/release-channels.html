指南

发布通道

stable | canary | preview。槽位指定通道，注册表在每次请求时把它解析成版本和 serviceUrl —— 所以上线一个新的片段构建不需要重建页面。

注册表文件

registry/registry.data.json，加载时由 FragmentRegistrySchema 校验：

{
  "fragments": {
    "promotion-banner": {
      "stable":  { "version": "0.1.0", "serviceUrl": "http://localhost:4201",
                   "manifestUrl": "http://localhost:4201/manifest" },
      "canary":  { "version": "0.2.0-beta.1", "serviceUrl": "http://localhost:4201", "…": "…" },
      "versions": { "0.1.0": { "…": "…" } }
    }
  }
}

versions 是让回滚成为可能的历史。registry/releases.json 是只追加的晋级日志。

不要手编辑这两个文件。用 CLI —— 它们以原子方式写入、带咨询锁和乐观内容哈希校验，遇到并发改动时打印 {"status":"conflict","retry":true} 而不是覆盖掉别人的改动。

一次发布

# 1. 部署镜像（你的平台的事）
# 2. 把 canary 指向新版本
pnpm exec tsx scripts/register-fragment.mts --name order-book --version 0.2.0 \
  --service-url http://order-book.internal --channel canary
# 3. 确认是哪个构建在应答
curl -s http://order-book.internal/health   # {"status":"ok","version":"0.2.0",…}
# 4. 晋级
pnpm exec tsx scripts/promote-fragment.mts --name order-book
# 5. 不对就退回去
pnpm exec tsx scripts/rollback-fragment.mts --name order-book

不写注册表也能改指向

<FRAGMENT_NAME>_URL 在运行时覆盖目标 —— ORDER_BOOK_URL、PRICE_PANEL_URL（fragmentEnvVarName 会转大写并替换非字母数字字符）。值必须能解析为 URL，否则注册表加载时就抛错并点名出错的变量，而不是等到 fetch 时才失败。

它改写 serviceUrl 和 manifestUrl，但不改写 assetsUrl —— F2。

解析

import { resolveFragment } from "@mvp/runtime";
resolveFragment(registry, "order-book", "canary");   // 按通道
resolveFragment(registry, "order-book", "0.1.0");    // 按确切版本
// -> { version, serviceUrl, manifestUrl } | null

null 表示该通道上没有注册。指向片段所没有的通道的槽位会静默地解析成它的降级内容 —— 没有任何构建期检查保证每个槽位的通道在注册表里存在。

demo 的真实状态

在把这套生命周期当真之前值得知道：14 个片段里有 12 个只有 canary 条目。只有 promotion-banner（stable + canary）和 recommendation-widget（stable）带 stable，而 page-trade、page-markets、page-portfolio 的每一个槽位挂的都是 channel: "canary"。晋级路径只在 2 个单元上被操练过（F6）。

recommendation-widget 另外还没有 versions 历史，所以 rollback-fragment 会因为没有记录目标而正确地拒绝它。
