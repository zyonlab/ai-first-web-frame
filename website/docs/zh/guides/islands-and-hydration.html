指南

岛屿与水合

片段输出 SSR HTML 加一段内联 JSON 快照。页面在这段标记之上水合一个 React 岛屿 —— 但只有版本握手通过才会。

标记契约

<div data-island="orderForm">
  <script type="application/json" data-island-props="orderForm">
    {"props":{…},"slice":"trade.order-draft","fragment":"order-form",
     "version":"0.1.0","contractHash":"…"}
  </script>
  <!-- 服务端渲染的标记 -->
</div>

IslandSnapshotSchema：props（record，默认 {}），以及可选的 slice、fragment、version、contractHash。

注册与水合

import { registerIsland, hydrateIslands } from "@mvp/islands";
import { OrderFormIsland, OrderFormIslandPropsSchema } from "@mvp/fragment-order-form/island";

registerIsland("orderForm", OrderFormIsland, {
  expect: { fragment: "order-form", version: "0.1.0" },
  propsSchema: OrderFormIslandPropsSchema,
});

hydrateIslands(document);   // 找到每个 [data-island]，挂载通过检查的那些

其他入口：mountIsland（单节点）、readIslandSnapshot、getIsland、clearIslandRegistry、configureIslandRuntime。

握手，以及失败意味着什么

以下四种原因之一会导致跳过水合、原样保留 SSR 标记（SnapshotMismatchInfo.reason）：

原因成因
version-mismatch快照 version ≠ 页面期望的版本
contract-hash-mismatch同一版本下载荷契约变了
invalid-snapshotJSON 不满足 IslandSnapshotSchema
invalid-props快照 props 通不过岛屿自己的 propsSchema

跳过就是失配情形下的成功路径。一个在没有品种 tick size 和 lot size 的情况下水合出来的下单表单，会接受交易所必然拒绝的订单 —— 那才是失败。

装一个 handler 来观测它：

configureIslandRuntime({
  onSnapshotMismatch: (info) => reportDrift(info),  // {island, expected, actual, reason}
});

这也是本设计相对 Module Federation 的诚实边界：MF 会协商并加载匹配版本；我们只检测并拒绝。这里没有运行时远程加载。

给岛屿加必填 prop 是破坏性变更

如果你给某个岛屿的 propsSchema 加一个必填字段，所有由旧版片段产出的 SSR 快照都会 invalid-props 失败，那些岛屿会停止水合 —— 这是设计如此。要么先升版本并滚动发布片段，要么把字段设为可选并给安全默认值。

这不是理论：给下单表单的 props schema 加了三个必填字段之后，一份手工构造的测试快照立刻停止水合 —— 而这正是旧片段遇上新页面 bundle 时你希望线上发生的行为。

预算

岛屿是客户端 JS 的主要成本。每个片段的 jsBytes 以「其客户端入口经 esbuild 压缩后的体积，且 react、react-dom、@mvp/* 全部 external」计量 —— 共享 vendor 算在消费它的页面头上，而不是每个片段重复计费。由 audit:bundle 强制。

目前有 4 个岛屿超过了建议性的 large-client-component 体积参考线（F10）。
