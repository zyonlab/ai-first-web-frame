性能预算

每个单元都声明预算。其中一部分由 pnpm verify 强制，一部分只由一个独立的运行时闸门强制，还有一部分哪里都没人管。这一篇把它们分清楚。

把这个差别写在最前面，是因为顶层那句「预算是硬闸门」只对 schema 的一部分成立。

声明

每个单元一份 src/budget.ts，由 PerformanceBudgetSchema 校验，scope 取 component | fragment | page | shell。

export const orderBookBudget = loadDefaultBudget("fragment", "order-book");

到底哪些被强制

字段作用域由谁强制属于 pnpm verify？
jsBytescomponent、fragment、pageaudit:bundle是
cssBytesfragment、pageaudit:css是
maxTTFBMspagepnpm verify:runtime否 —— 需要一个活的 URL
maxLCPMspagepnpm verify:runtime否
maxCLSpagepnpm verify:runtime否
rscPayloadBytespage—否（运行时才可测，已被承认）
maxNetworkRequestspage—无人管
maxINPMspage—无人管
maxFragmentLatencyMsfragment—无人管
maxRenderMsfragment—无人管
maxMemoryMBfragment—无人管

也就是说：11 个字段里 2 个闸住构建，另 3 个只在你对一个运行中的栈执行独立检查时才闸住，剩下 5 个是文档。见 F11。

对工具公平地说一句：audit:bundle 在自己的输出里就说清楚了边界 —— reports/bundle-report.json 带一个 notes 数组声明运行时指标不在闸门内，还有一个 unmeasured 列表逐条说明为何跳过。

被测的那几个是怎么测的

  • 片段 jsBytes —— 该片段客户端入口经 esbuild 压缩后的体积，react、react-dom、@mvp/* 全部 external。共享 vendor 算在消费它的页面头上，不向每个片段重复计费。没有客户端入口的片段测得 0。
  • 页面 jsBytes —— 从 .next 构建 manifest 读出的首屏客户端 JS，gzip 后字节。
  • cssBytes —— 由 audit:css 从源 CSS 计算，同时报告总量/无用/重复字节、全局选择器数和 !important 数量。

预算失败时

缩小客户端入口、把逻辑移到 SSR，或者拆分片段。把 budget.ts 里的数字调大是一个决定，不是一个修复 —— 在提交信息里写清楚为什么。
