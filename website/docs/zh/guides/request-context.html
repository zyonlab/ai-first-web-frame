请求上下文

一个经校验的对象随每次渲染同行，跨进程边界时以 HTTP 头形式传播。

形状

RequestContextSchema（@mvp/contracts），必填字段在前：

字段类型说明
traceIdstring，≥8把片段的 span 串到同一次页面请求上
requestIdstring，≥4
localestring，≥2
tenantstring，≥1
featureFlagsrecord必填，可以是 {}
timestampISO datetime
experimentrecord<string>默认 {}
themelight|dark|system默认 system
devicemobile|tablet|desktop|bot|unknown默认 unknown
userAgentstring默认 ""
user、session、ip可选
extensionsrecord<string>默认 {} —— 见下
import { createRequestContext } from "@mvp/request-context";
const ctx = createRequestContext({ headers: { "x-locale": "en-US", "x-tenant": "acme" } });

访问器：getLocale、getTenant、getTraceId、getUser、getFeatureFlags、getContextExtension。

加一个维度，而不动框架

错误做法是去加宽 RequestContextSchema —— 那是一个框架包，而分层规则禁止产品代码修改它，所以「加个字段」就等于为了业务需要去加宽框架。

正确做法是 extensions：

const ctx = createRequestContext({
  headers,
  extensions: { abBucket: "b", acquisitionChannel: "paid-search", tier: "gold" },
});

getContextExtension(ctx, "abBucket"); // "b"

值是字符串，因为它们要跨 HTTP 边界。每一个以 x-mvp-ctx-<name> 传播（CONTEXT_EXTENSION_HEADER_PREFIX）。

这是 @podium/context 的 .register(name, parser) 扩展点的 schema 校验版等价物。

跨线传输

import { serializeContext, deserializeContext } from "@mvp/request-context";
const headers = serializeContext(ctx);   // -> 扁平的头记录
const ctx2 = deserializeContext(headers);

上下文与缓存

槽位上的 cachePolicy.vary 指名切分其缓存键的上下文维度。输出依赖 tenant 的片段必须声明 vary: ["tenant"]，否则两个租户会共享同一条缓存。createFragmentCacheKey 负责构键，createDataKey 对数据源做同样的事。

宽容层

POST /render 接受部分上下文：parseFragmentRenderRequest 先试严格 schema，再试一个 ctx 为 .partial().optional() 的信封，两者都失败才返回 400。用 curl 手工测服务时很方便；至于为什么你目前观测不到线上流量是否落在那一层，见 F14。
