构建

pnpm build 很慢

第二次起不该慢。build 和 test 走 Turborepo（turbo.json）；热缓存能把 pnpm verify 从约 165 秒压到约 32 秒，而且 Turborepo 会从缓存恢复被删掉的 dist/ 和 .next/，而不是重建。

如果每次都在全量重建，说明有东西在让缓存失效。两条规则：

  1. 任务从自己包之外读取的任何东西都必须声明，否则缓存会返回一个过期的「通过」。packages/mcp/turbo.json 是范例 —— 它的测试 shell out 到 scripts/*.mts，后者读 registry/*.json 和页面 manifest，所以这些被列为 $TURBO_ROOT$ 输入。
  2. 会改变任务行为的环境变量进 globalEnv；只用于寻址外部环境的值（*_URL、密钥）进 globalPassThroughEnv，这样它们永远不进缓存键。

任何 globalDependencies 条目（pnpm-lock.yaml、根 package.json、tsconfig.base.json、vitest.config.ts、biome.json、oxlint.json、dependency-audit.json）的变化都会按设计让全部缓存失效。

找不到某个 @mvp/* 包

该包的 dist/ 缺失或过期。跑 pnpm build。不要为了绕开而从 src/ import —— 包的 exports 是刻意指向 dist/ 的。

如果这发生在全新克隆的 pnpm test 期间，前置构建本应处理掉它；请读构建错误而不是测试错误。

新导出子路径在测试里解析不了

Vitest 别名由 scripts/workspaceAliases.mts 从各包的 exports 映射推导。生成器读的是导出目标，不是子路径名 —— @mvp/fragment-order-book/patch 映射到 src/ladder.ts，所以从名字猜 src/patch.ts 是错的。把子路径加进 package.json 的 exports，别名会自动跟上，不需要手改任何东西。

只有某一个页面应用 next build 失败

页面应用是独立可部署物，各有自己的 tsconfig.json。只构建那一个：

pnpm --filter @mvp/page-trade build

tsgo 与 tsc

pnpm typecheck 用 tsgo 跑各 project 的 tsconfig，并写出 reports/typecheck-report.json（每个 project 一条结果）。pnpm typecheck:legacy（tsc -b）作为兜底保留，用于 tsgo 诊断信息不清楚时 —— 它更慢，边界情况下偶尔与 tsgo 有分歧。

Docker

docker compose -f infra/docker/docker-compose.yml config   # 注册片段后校验
docker compose -f infra/docker/docker-compose.yml up
pnpm smoke                                                  # 对运行中的栈做健康检查

每个片段一个 Dockerfile。register-fragment --with-compose 会加入服务，并拒绝已被占用的端口；遇到冲突就显式传一个空闲的 --port。

浏览器 vendor bundle

page-trade 为「岛屿经 import map 加载」这个探索构建了一份自托管 vendor bundle：

pnpm --filter @mvp/page-trade build:spike-vendor

产物落在 apps/page-trade/public/spike-vendor/（已 gitignore，按需构建）。它从 node_modules 打包 react、react-dom/client、react/jsx-runtime、@mvp/trade-contracts 和 @mvp/ui/shadcn，所以它跟随你实际安装的 React 版本。不从任何 CDN 拉取。
