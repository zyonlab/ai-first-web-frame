Performance budgets

Every unit declares a budget. Some of those numbers are enforced by pnpm verify, some are enforced only by a separate runtime gate, and some are declared and enforced nowhere. This page says which is which, because the difference matters and the top-level claim "budgets are hard gates" is only true of part of the schema.

Declaring

src/budget.ts per unit, validated by PerformanceBudgetSchema with scope one of component | fragment | page | shell.

export const orderBookBudget = loadDefaultBudget("fragment", "order-book");

So: 2 of 11 fields gate the build, 3 more gate a separate runtime check you must run against a running stack, and 5 are documentation. See F11.

The bundle audit is honest about this in its own output — reports/bundle-report.json carries a notes array saying runtime-only metrics are not gated, and an unmeasured list explaining each skip.

How the measured numbers are measured

  • Fragment jsBytes — minified esbuild bundle of the fragment's client entry with react, react-dom and @mvp/* external. Shared vendor is charged to the consuming page, not billed to each fragment. A fragment with no client entry measures 0.
  • Page jsBytes — gzipped first-load client JS read from the .next build manifests.
  • cssBytes — from source CSS, by audit:css, which also reports total/unused/duplicated bytes, global selector count and !important count.

When a budget fails

Shrink the client entry, move logic to SSR, or split the fragment. Raising the number in budget.ts is a decision, not a fix — record why in the commit.

Runtime gate

pnpm verify:runtime --url http://localhost:4100/trade/BTC --json

Checks web-vitals-lcp, web-vitals-cls, web-vitals-ttfb against the page budget. When a metric cannot be collected the check reports skip rather than silently passing — so an absent measurement is visible. There is no INP check, despite every page declaring maxINPMs.
