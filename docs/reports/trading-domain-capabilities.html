你问的四件事，分别落在系统的哪一层

把问题按合约交易页（apps/page-trade，9 个片段槽位）这个真实场景展开： React 新特性支持到哪、数据怎么按实时性分区、跨层与跨微组件怎么共享、不同创建时机怎么处理、设计系统能不能独立交给 UI 组维护。 每条都指到具体文件，并标出已支持 / 部分支持 / 缺口。

先给结论：数据分区与跨组件共享这块是这个系统最成熟的部分 —— 五档新鲜度 × 四档隐私 × 契约总线已经成体系， 你举的六类交易数据全部已有对应的 source 定义。React 侧是 18.3 + Next 15，流式和选择性水合都有，但吃不到 React 19 的新能力。 设计系统已经是独立三层，可以直接交给 UI 组维护。最大的缺口在实时数据的跨片段分发与交易约束的强制执行。

01

React 特性支持度

版本是 React 18.3.1 + Next 15.3.4。Next 15 本身支持 React 19，但这个仓库锁在 18.3，所以能力边界很清楚：

能力状态在交易页的体现
SSR 流式 / Suspense 分块已支持streamFragmentSlots 每槽位一个 promise，<FragmentSlotStream> + <Suspense> 谁先好谁先 flush。但交易页有意不用 —— 它的 trade-nav.test.tsx 用纯 react-dom/server 渲染页面，而那跑不了 Next RSC 运行时之外的 async Server Component。首页/markets/portfolio/product 四页在用。
Server Components已支持页面与诊断区块都是 async Server Component；片段本身是独立 HTTP 服务，不走 RSC 而走 POST /render 返回 HTML 串。
选择性水合（islands）已支持@mvp/islands：片段 SSR 出 <div data-island="orderForm">，页面 bundle 注册组件后 hydrateIslands() 只水合这些节点。交易页 4 个 island：market-header / chart-panel / account-bar / order-form。
脱水 / 再水合（dehydrate → hydrate）已支持这正是 island snapshot 机制：片段把 props 序列化进内联 <script type="application/json" data-island-props>，客户端 mountIsland 解析 + Zod 校验后再 createRoot().render()。等价于 react-query 的 dehydrate/hydrate，但带版本握手。
水合失配的处理强于常规快照带 {fragment, version, contractHash}，页面用 registerIsland(name, comp, { expectedVersion, expectedContractHash, propsSchema }) 声明期望。不匹配完全跳过水合（不建 root），SSR HTML 保持为最终静态态 + warn + onSnapshotMismatch 回调。
React 19：use()、Actions、useOptimistic、useFormStatus不支持下单的乐观更新目前靠 @mvp/interaction 的 defineMutation + slice store 手写，不是 useOptimistic。
React 19：<meta>/<link> 自动提升到 head不支持这条刚踩到过：页面组件里渲染 <meta> 会落在 <body>（实测），所以页面健康标记改用了 <div hidden data-mvp-page-health>。
React 19 Compiler不支持—
部分预渲染（Next PPR）未启用所有组合页都是 export const dynamic = "force-dynamic"。

升 React 19 的代价 评估

主要卡点是 page-trade 的测试策略：它用 react-dom/server 直接渲染页面来做断言，这条路在 React 19 下仍然跑不了 async Server Component。 升级本身（18.3 → 19）对 island 运行时影响不大（createRoot/hydrateRoot API 未变），收益是 useOptimistic（下单/撤单的乐观 UI 天然契合）、meta 自动提升、以及 Actions 简化表单提交。 建议把它当成一条独立的技术债，而不是顺手做。

02

全局业务数据分区：实时 / 非实时

分区不是靠约定，而是写进契约并在定义期强制校验的。每个数据源声明两个正交维度：

DataFreshnessSchema = static | build-time | isr | request-time | near-realtime | realtime | client-local DataPrivacySchema = public | tenant | user-segment | user-private

defineDataSource() 在模块加载时就跑 safeParse，所以下面这些不变式是会抛 DataDependencyError 的，不是文档里的建议：

  • user-private 的数据不能是 static —— 用户持仓不可能被静态缓存
  • realtime 的数据不能配 TTL 缓存 —— 盘口配 ttl 是自相矛盾
  • subscription 类型的源必须是 realtime

全部已有定义（domains/trade-data/src/tradeSources.ts，850 行），id 由 sourceIds 统一构造，禁止手拼字符串：

03

跨层 / 跨微组件的数据共享

你描述的两个场景，系统用的是两条完全不同的通道，选哪条取决于「水合前还是水合后」。

场景 A · 顶层提供数据 → 跨层最底层微组件消费（服务端，水合前）
1页面在 manifest.slots.json 里给槽位声明 dataDependencies: ["account"]。order-form / account-bar / positions-table 三个槽位都声明了同一个 account。
2调度器建 DAG：data:account 成为一个节点，三个 slot:* 节点依赖它。拓扑分层后 data 先于 slot 执行。
3页面的 resolveData(id) 回调用 createDataClient 读一次；三个槽位共享这一次解析（请求级去重，调度器还会发 duplicate-data-resolution 提示）。
4片段通过 POST /render 的 props 拿到结果 —— 不需要逐层透传，页面和片段之间没有 React 组件树，是 HTTP 边界。
5失败传播：account 节点失败，三个下游槽位一起变 skipped-dependency 并降级；required 的那个还会让页面答 503。

这条路径解决的正是「跨层」问题：传统 React 里要 context 或 props drilling，这里是声明式依赖 + 调度器编排，深度无关。

场景 B · 微组件 A 产出 → 微组件 B 消费（客户端，水合后）
1频道在 domains/trade-contracts/src/slices.ts 里冻结声明：TRADE_ACTIVE_SYMBOL、TRADE_ORDER_DRAFT_PRICE、TRADE_LEVERAGE、TRADE_HOVERED_PRICE、TRADE_CHART_INTERVAL、TRADE_BOOK_GROUPING 等 7 个。
2每个频道的契约指定 唯一 publisher + subscriber 白名单 + payloadSchema。非 publisher 发布会抛 InteractionContractError —— 这是 ACL，不是约定。
3页面只创建一个 createSliceStore 和一个 createInteractionBus（apps/page-trade/src/tradeStore.ts，模块级 memo），在水合引导时注入每个 island。
4真实流：点盘口某一档 → order-book 发布 TRADE_ORDER_DRAFT_PRICE → order-form 订阅并填入价格。跨两个独立部署的片段，靠共享总线。
5SSR 状态的接续：initialTradeSlices 是 store 的种子（symbol: "BTC"、leverage: 1…），所以水合前后状态连续。

这里有个必须知道的陷阱：孤儿总线 已被门禁拦截

createInteractionBus 实例彼此隔离。island 自己 new 一个总线，publish/subscribe 本地都通，但对页面的共享总线完全不可见 —— 没有报错、没有警告，就是一条死链路。历史上 account-bar 就因此收不到 order-form 的杠杆变更。

正确写法是 props.bus ?? 自建 fallback（fallback 只为片段独立渲染/测试存在）。audit:deps 的 island-bus-without-escape-hatch 规则会 fail 掉任何没留逃生口的 island.tsx。

实时数据的分发：现状与缺口

@mvp/data 提供 subscribeData(id, handler) + 可插拔 SubscriptionTransport， domains/trade-data 提供确定性的 mock 实时传输（种子 PRNG 生成帧）。 但订阅是在页面层集中起的（apps/page-trade/src/realtime.ts，542 行），它订阅 book.l2 / trades / positions，然后直接 patch DOM（不是 React 重渲染）。

缺口：片段无法自己声明「我要订阅什么」 缺口

槽位可以声明 dataDependencies（一次性读），但没有对应的 subscriptions 声明。所以「某个微组件产出全局实时数据、另一个微组件消费」目前必须由页面代码手工编排：页面知道要订哪些源、知道要 patch 哪些 DOM 选择器。片段自己是被动的。

后果：新增一个需要实时数据的片段，要改页面的 realtime.ts —— 这违背了「挂载一个片段不用改页面」的设计目标。详见 §06 缺口 1。

切币对时的失效 部分支持

切 symbol 时，TRADE_ACTIVE_SYMBOL 在总线上广播，islands 各自响应。数据侧的 source id 天然按 symbol 分区（book.l2.BTC vs book.l2.ETH），所以缓存不会串。

但：页面级的 props.symbol 是靠 fragmentSlots.ts 里一个 {...slot, props} 的每请求合并实现的 —— 这是 page-trade 独有的手写胶水，不是框架能力。换句话说，「按路由参数给所有槽位注入同一个 prop」这件事没有被抽象。

正是你要的那个东西 —— 业务写 CSS 时只碰这些，不碰组件内部：

/* 框架语义层（UI 组拥有，主题切换自动生效） */ --mvp-color-accent --mvp-color-ink --mvp-color-border --mvp-color-surface-* --mvp-color-text-muted --mvp-color-buy --mvp-color-sell --mvp-color-up --mvp-color-down --mvp-font-body --mvp-font-mono --mvp-spacing-md --mvp-z-* /* 交易域别名层（业务组拥有，是上面那层的主题感知别名） */ --trade-buy --trade-sell --trade-up --trade-down --trade-panel-bg --trade-panel-border --trade-row-hover --trade-flash-buy --trade-flash-sell --trade-chip-active --trade-text --trade-font-mono

这个两段式是关键：UI 组改 --mvp-color-buy 的色值，所有交易片段自动跟随； 业务组想给交易场景单独调（比如盘口行 hover 更重），改 --trade-row-hover 即可，不需要碰 UI 组的包。 主题切换由 <html data-theme> 驱动，createAllThemeVariables() 一次性注入 light+dark 两套，无闪烁。

交接给 UI 组需要约定的三件事 现成机制

① 版本与发布：这三个包已经是独立 workspace 包，可以独立发版；业务侧升版本即可。
② 防重复造轮子：audit:similarity 会 fail 掉和现有组件相似度 ≥0.82 的新组件（当前扫 22 个 .tsx）。
③ 预算：CSS 字节数有硬门禁 —— 不过页面级目前测不到（样式是请求时字符串注入的，审计如实标 unmeasured），片段级是真的在测（如 order-book 2176 / 10000 字节）。

一个现实约束 注意

@mvp/ui 把 7 个 Radix 包 + cmdk + tailwind-merge 列为 dependencies 而非 optional，所以任何依赖 @mvp/ui 的片段镜像都会装上 Radix —— 哪怕它只用了 server-safe 的那 7 个原语。要给 UI 组独立发版前，建议先把 shadcn 那层拆成独立包或 optional peer。

06

针对合约交易场景的三个缺口

缺口 1 · 片段不能声明实时订阅 最影响你的场景

槽位能声明 dataDependencies（一次性读），没有 subscriptions 的对应物。所有实时订阅集中在页面的 realtime.ts（542 行），它硬编码了订阅哪些源、patch 哪些 DOM 选择器。

对你的影响：新增一个吃实时数据的片段（比如「爆仓提示」「资金费倒计时」），必须改页面代码 —— 而框架的核心承诺是「挂载片段不用改页面」。

建议：给 SlotSchema 加 subscriptions?: string[]，由运行时统一订阅并把帧按片段分发（片段声明自己的 patch 入口，像现有的 @mvp/fragment-*/patch 约定）。估 1–2 人周。

缺口 2 · 交易约束没有强制执行点 风险

symbol.meta 提供了 tickSize / lotSize / priceDecimals / sizeDecimals / maxLeverage，leverage.tiers 提供了阶梯 —— 但它们只是数据，没有任何地方强制校验下单入参符合这些约束。

defineMutation("placeOrder") 的 input schema 只校验字段类型（symbol/side/type/size/leverage 是不是 number/string），不校验「size 是否是 lotSize 的整数倍」「leverage 是否超过该币对该档位的上限」「price 是否对齐 tickSize」。

建议：在 domains/trade-contracts 加一层纯函数校验器（validateOrderAgainstSymbol(draft, meta, tiers)），下单前 island 调一次、服务端 mutation 再调一次。纯函数、好测、两端复用。估 3–5 人日。

缺口 3 · SymbolMetadata 字段可能不够 待确认

现有六个字段覆盖了 tick/lot/小数位/最大杠杆。你提到的「最小开单数量」目前只能用 lotSize 表达 —— 如果业务上「最小下单量」和「数量步长」是两个独立值（多数交易所是），需要扩字段；「风险限额」目前在 leverage.tiers 的 maxNotional 里，若还要按用户等级/仓位模式细分，也要扩。

扩字段本身成本很低（改 SymbolMetadata 类型 + 生成函数），关键是先把业务上真正需要的约束列全再一次性加，避免反复改契约。

07

一页纸总结

你的问题落在哪一层结论
React 水合 / 去水 / 流式@mvp/islands + @mvp/runtime（react.tsx）已支持 选择性水合、快照脱水再水合、版本握手、流式分块；但锁在 React 18.3，吃不到 19 的 useOptimistic/Actions/meta 提升
数据实时/非实时分区@mvp/contracts（枚举+不变式）+ @mvp/data + domains/trade-data成熟 七档新鲜度 × 四档隐私，定义期强制校验；你举的六类数据全部已有 source
顶层→底层跨层共享manifest.slots.json 的 dataDependencies + 调度器 DAG已支持 声明式依赖，请求级去重，失败传播；无需 props drilling
微组件↔微组件实时共享@mvp/interaction + @mvp/store + domains/trade-contracts部分 契约总线 + ACL 已成熟（水合后）；但实时订阅仍需页面手工编排
不同创建时机三条正交轴：渲染策略 / 新鲜度 / 缓存维度已支持 币对基础信息 isr 300s、杠杆阶梯 static 86400s，按 tag 定向失效

优先级建议：如果要把这套东西真正用在合约交易业务上，先做缺口 2（交易约束强制执行） —— 它是资金安全相关，3–5 人日； 再做缺口 1（片段声明订阅） —— 它决定了这套微前端在实时场景下能不能真正「加片段不改页面」，1–2 人周。 React 19 升级可以往后放，它是体验改善不是能力缺失。
