01

这个仓库在做什么

表面上：一个 pnpm monorepo，里面有 1 个 shell 网关、7 个 Next.js 页面应用、14 个 Fastify SSR 片段服务， 外加一个用来演示的加密交易前端（trade / markets / portfolio / vaults / referrals）。 页面在服务端通过 POST /render 把片段的 HTML 拉回来拼装，片段挂了就降级成 fallback，页面照常 200。

但真正的产品面不是那个交易 demo，而是框架本身外露的那套接口。它同时解决两类问题：

  • 组织问题——让 22 个单元能各自独立开发、独立构建、独立上线，而不互相把对方搞挂。 片段升级一个版本只重建它自己和挂载它的页面，其他 20 个单元完全不动。
  • 协作介质问题——让「多个 agent 并行改同一个仓库」这件事是安全的。 每个动作有 CLI、有 JSON 信封、有原子写 + 冲突重试、有 MCP 工具；每条约定背后有一道会 fail 的门禁， 而不是 CLAUDE.md 里的一句劝告。

llms.txt 把这个意图写得很直白：“Consumers are AI agents operating the lifecycle CLIs, not humans reading prose.” 所以所有文档都偏向精确签名、JSON 信封和可复制的 Accept: 判据。

代码怎么分层、怎么分模块

三层导入规则：只能向下

可部署单元apps/ · fragments/
8 个 app（网关 + 7 页面）与 14 个片段服务。每个有自己的 Dockerfile、budget、health。可以 import domains 和 packages。
↓ 允许
领域层domains/
交易 demo 的业务词汇：trade-contracts（slice 频道 id、mutation、纯 reducer）、trade-data（数据源注册 + 确定性 mock 实时流）、trade-prefs、trade-theme、trade-chart。只能 import packages。
↓ 允许（反向 import 会被 audit:deps 的 domain-code-in-framework-package 规则打回）
框架层packages/
19 个 @mvp/* 包，零业务词汇。永不向上 import。

这条规则的价值在于它是被审计工具执行的，不是 review 时靠眼睛看的：把 “buy/sell” 这种词写进 packages/ui 会让构建失败。 domains/ 因此成了「加一个新业务领域」的参照实现，而框架包始终保持可复用。

04

四条生命周期

这个仓库里「生命周期」不是一个词，而是四条正交的链路：一次请求的、一个片段交付的、一个 island 在浏览器里的、一次变更走到生产的。 四条各自都有独立的失败语义和门禁。

A · 请求生命周期（毫秒级）

manifest.slots.json → DAG → 并行取片段 → 流式吐出
  1. 声明：页面的 manifest.slots.json 是唯一真相——槽位名、片段、channel、策略、超时、props、cachePolicy、dependsOn、dataDependencies、required。手工编辑被禁止，只能由 mount-slot 写。
  2. 建计划：createSlotDataExecutionPlan 用 slot:<name> 和 data:<id> 建节点做拓扑分层，每层 Promise.all。重名、指向不存在节点的边、环，在建计划时就 throw。
  3. 取数：每槽位 slot.timeoutMs ?? 200ms 竞速；响应必须过 parseFragmentRenderResponse，schema 不合法的响应直接降级并把违规记进 trace span 的 error——不会被静默 cast。
  4. 降级隔离：慢 / 挂 / 未注册的槽位退化成 createFallbackResponse（TTL 5s，标记 metadata.fallback），永不 reject、永不打断页面。失败的 data 节点 或失败的 required 槽位 会把下游置为 skipped-dependency；非 required 只拖累自己。超时同时触发 abort 取消上游请求，兜底标记一律用片段名（不是内部 serviceUrl），reason 做 HTML 转义。
  5. 健康度：聚合出 ok / degraded / unhealthy，并额外吐出调度建议（长串行链、无谓 barrier、重复数据解析）。
  6. 流式：streamFragmentSlots 立刻返回——每个槽位一个 promise，谁先好谁先 flush（<FragmentSlotStream> + <Suspense>）。
渲染策略行为典型用法
static零网络，直接吐 staticHtml，TTL 一年page-home 编辑区块
ttl-cache取一次按 TTL 缓存；fallback 响应永不入缓存product 促销 300s、portfolio 盈亏图 60s
cached-ssr同一缓存路径，惯例用于短 TTL 准实时markets 表 5s、行情头 5s
dynamic-ssr每请求都取（默认策略）用户私有数据（portfolio 汇总 ttl:0）、盘口、成交流

缓存键由片段名 + 解析出的版本 + 策略 + vary 维度（默认 tenant / locale / experiment / props，device 需显式开启）组成。 缓存本身是有界的（默认 500 条，写入时先扫过期再按插入序淘汰最老的），并支持 invalidateFragmentCacheByTag() —— 槽位声明的 cachePolicy.tags 由此成为可用的失效依据而不是装饰。 注：旧的 isr 别名因为和 Next.js 的页面级 ISR 同名不同义，已被彻底从枚举里删掉——现在写 isr 会直接校验失败。

B · 片段交付生命周期（7 步，全部有 JSON 信封）

每一步：一个 JSON 对象到 stdout + 一条 Accept 判据 + 失败不落盘
01

Scaffold

生成 fragments/<kebab>/ 11 个文件，且开箱即跑：server.ts 是 host 适配器，端口从 4201 起自动取第一个空闲值，Dockerfile 真能构建，tsconfig.json 让新单元进入 pnpm typecheck 的发现范围。不碰注册表。

pnpm --filter @mvp/create-component start -- PricePanel --type fragment
Accept: "status": "created" · files.length === 11
02

Implement + Test（TDD）

先扩 render.test.ts 再改 render.ts。脚手架已经给了 200 与降级两条路径的断言。唯一机器信号是退出码。

pnpm --filter @mvp/fragment-price-panel test
03

Register

写注册表条目，可选同时补 docker-compose 服务（从 4201 起扫下一个空闲端口）。版本 append-only：同 name+version 换 URL 重注册会 throw，而不是悄悄改历史。

pnpm exec tsx scripts/register-fragment.mts --name price-panel --version 0.1.0 \ --service-url http://localhost:4203 --channel canary --with-compose
Accept: "status": "registered" · 重跑得到 "action": "unchanged"（幂等）
04

Mount

往页面 manifest 加槽位，并顺手重生成 fragmentSlots.gen.ts。挂载未注册的片段会失败（除非 --allow-unregistered）。--check 只比对不写盘。

pnpm exec tsx scripts/mount-slot.mts --page page-home --slot pricePanel \ --fragment price-panel --strategy dynamic-ssr --channel canary --timeout-ms 200
Accept: "status": "mounted" · warnings: []
05

Verify

14 道门禁全过，报告落 reports/verify-report.json（每步含 stdout/stderr 尾部 6000 字符，便于 agent 定位）。

pnpm verify
Accept: exit 0 · results 里没有 "status": "failed"
06

Promote（canary → stable）

把前一个 stable 版本记进条目的 versions 历史，并向 releases.json 追加一条。这条历史就是回滚目标。

pnpm exec tsx scripts/promote-fragment.mts --name price-panel
Accept: "status": "promoted" · from/to 符合预期
07

Rollback

回到 promote 时记录的版本，或显式 --to。没有可回滚目标时干净地失败（unchanged），而不是瞎猜。

pnpm exec tsx scripts/rollback-fragment.mts --name price-panel [--to 0.1.0]
Accept: "status": "rolled-back" · to 等于目标版本
08

Verify unit（最小部署单位自检）

把「一个片段能独立交付」变成一条命令：只构建该单元的依赖闭包 → 启动构建产物 → 断言 /health、/ready、/manifest 报同一个 manifest 版本、GET / 带版本标记 → 报告各 channel 当前指向的版本。

pnpm verify:unit --name price-panel [--port 4399] [--skip-build]
Accept: "status": "ok" · version 等于将要注册的版本

横切保证：未知 flag 直接拒绝（--chanel 会得到 “did you mean --channel?”，不写任何文件）； 写入是原子的（临时文件 + rename，外加 <file>.lock 建议锁和乐观内容哈希校验）； 并发冲突返回 {"status":"conflict","retry":true} —— 原样重跑即可。这三条合起来，才让「多 agent 并行操作同一份注册表」成立。

C · Island 生命周期（浏览器侧，两级独立性模型）

片段分两档。Tier 1（纯 SSR）：HTML 每次请求都从片段服务现取，部署完 promote 一下就上线，页面重建次数 0，版本错位根本不可能发生。 Tier 2（带 React island）：SSR HTML 同样即时生效，但 island 的客户端 JS 在构建期被静态 import 进页面 bundle，所以行为变更仍需页面重建。

关键是第二档的错位被检测而不是静默：

  1. 片段在 SSR HTML 里内联一个 <script type="application/json" data-island-props> 快照，盖上 {fragment, version, contractHash}。
  2. 页面 bundle 用 registerIsland(name, comp, { expectedVersion, expectedContractHash, propsSchema }) 声明它的期望。
  3. mountIsland 依次校验：快照 schema → 版本/契约哈希握手 → （若声明了）有效 props 的 propsSchema。
  4. 任一不通过就完全跳过 hydration——不创建 React root，SSR HTML 就是最终静态态，同时 console.warn 并回调 onSnapshotMismatch。没有 version 的老快照正常 hydrate（向后兼容）。

Island 之间的联动走 @mvp/interaction 的契约总线：每个频道声明唯一 publisher 和 subscriber 白名单，payload 逐次校验。 这里有一个被写成审计规则的著名坑——孤儿总线：island 自己 createInteractionBus() 时一切看起来都通， 但它和页面共享的总线完全隔离，跨 island 事件永远到不了，且没有任何报错。 修法是 props.bus ?? 自建 fallback，而 audit:deps 的 island-bus-without-escape-hatch 规则会 fail 掉任何没留逃生口的 island.tsx。

D · 变更交付生命周期（diff → 生产）

一份 diff，一个答案
  1. 算受影响集：仓库只有一个 affected 引擎（图引擎，老的路径启发式引擎已删）。单元依赖图不靠单独声明，而是直接读已有产物：片段 manifest、页面 manifest.slots.json、各 package.json、路由注册表、注册表数据。然后沿反向边做传递闭包。
  2. 收窄 vs GLOBAL：docs/、*.md、infra/、e2e/、tools/、CI 配置 → 什么都不触发；片段 / 页面 / 包 / domain 目录 → 收窄到该单元及其依赖者；注册表数据 JSON → 内容 diff 后只 seed 变更的片段；而 packages/registry/routes 的代码、根配置、任何无法识别的路径 → 保守走 GLOBAL。
  3. 门禁：pnpm verify 14 关（见下），再加 pnpm verify:runtime —— 用真 Chromium 跑组合后的页面，断言 verify 看不见的那一层：控制台/页面错误（含 React #418 hydration）、声明的静态资产是否真送到（没有 404）、有没有「内容悬在一大片空洞上方」、有没有页面溢出、招牌交互（点盘口某档 → 订单表单价格变化）还灵不灵。
  4. 出包与上线：CI 按受影响单元跑 docker 构建矩阵，打 <unit>:<git-sha> + :latest；compose 冒烟检查从注册表推导（注册一个片段就自动扩展冒烟范围）；k8s 覆盖全部 22 单元，服务间用显式 env 连线且 URL 在启动时就被 z.string().url() 校验。

最重要的价值：六条

如果只能从这个仓库带走六个想法，是下面这些。它们的共同点是：把「本来靠纪律维持的东西」改造成结构上不可能违反的东西。

1 · 漂移不是被检测，而是结构上不可能

页面槽位有两份表达（声明式 manifest 和运行时数组），这是经典的双写漂移源。这里的解法是 codegen： mount-slot 每次成功写 manifest 后重生成 fragmentSlots.gen.ts，手写的 fragmentSlots.ts 退化成薄壳， 只留 static manifest 表达不了的每请求胶水（timeout 覆盖、resolveData、page-trade 的每请求 props.symbol 合并）。 --check 纯比对、verify:manifest-gen 对每个页面跑一遍并入 verify。旧的 manifestSync.test.ts 保留为双保险。

2 · 契约在边界真的 .parse()，且诚实标注哪些没有

4 · 降级是产品特性，所以它有两档断言

边界与现状

这个仓库有个难得的习惯：把未完成的部分写成清单而不是藏起来。下表分两类——仍存在的，和本轮加固中已修复的（后者保留在这里，是因为「原来是什么样」本身解释了这些机制为什么长成现在的样子）。 运维配置类（镜像结构、k8s、指标、CDN）本轮明确不在范围内。

镜像是单阶段、无多阶段构建 仍存在22 份 Dockerfile 全部 COPY . . 在 pnpm install 之前，依赖层缓存必然失效；最终镜像带全部 devDependencies 和整仓库源码。本轮明确不在范围内（各家有自己的部署体系），但它是镜像体积与 CI 时长的主因。
页面应用没有 /metrics，灰度链路是断的 仍存在网关和 14 个片段都有 /metrics，7 个 Next 页面没有，所以 Argo 的 success-rate/latency-p95 AnalysisTemplate 查不到它的灰度目标 page-product。k8s 侧同样仍缺 HPA / PDB / Ingress / NetworkPolicy / ServiceMonitor。
覆盖率门禁未开 仍存在阈值配了、@vitest/coverage-v8 装了，但默认 pnpm test 路径不生成覆盖率报告（本地 coverage 模式反复卡死）。README 把「90% 覆盖率」列为生产前的第一个后续门禁。
CONTRACTS.md 仍是手工维护 仍存在文档自己标了新鲜度免责声明：目标状态是生成式索引，在那之前 schema 变更后应先看 packages/contracts/src/index.ts。
总线频道是裸 string 仍存在 · A2 gap拼错频道名在运行时才炸（InteractionContractError），不在 typecheck。缓解办法是永远从领域常量 import（如 TRADE_ACTIVE_SYMBOL），不写字面量。
片段宿主样板已抽走 已修复14 份各 130–188 行、约 90% 雷同的 server.ts 加 14 份 observability.ts（合计 2,718 行）收敛为 @mvp/fragment-host 285 行 + 14 份约 40 行适配器。防回归靠 audit:deps 的 fragment-server-not-hosted 规则，不是相似度阈值。
