架构与分层：规则是真的，有两处有意越层

apps/fragments → domains → packages 的单向规则不是文档约定而是程序： audit:deps 的 domain-code-in-framework-package 规则实跑 0 违规， audit:boundary 检查了 251 个文件。这是这个仓库最硬的一块。同时代码里有三处值得知道的现实：

A-01通用网关并不领域无关

apps/shell-gateway/src/server.ts 直接 import @mvp/trade-prefs（domain 层）来实现 /_shell/theme 和 /_shell/locale 的偏好写入。 分层规则允许（apps 可以依赖 domains），但意味着换一个业务域时网关要改。属于可接受的技术债，值得显式记账。

apps/shell-gateway/src/server.ts:13 — import { writeLocalePreference, writeThemePreference } from "@mvp/trade-prefs"
A-02Tier 2 片段是页面的构建期依赖，这在代码里一目了然

page-trade 通过子路径导出直接静态 import 四个片段的 /island、/manifest、/render。 「独立部署」在 Tier 2 只对 SSR HTML 成立，客户端行为确实被构建冻结——文档说得对，代码也确实这样。 顺带的隐性成本：这些子路径必须手工登记进根 vitest.config.ts 的 alias 表（约 110 行手写映射，含领域专属条目），而没有任何门禁校验这张表的完整性。

05

SEO：地基对了，门面几乎没做

先说好的：这套架构对 SEO 的结构性前提是正确的——SEO 关键内容确实在首屏 HTML 里，片段是服务端拼装， e2e/no-js.spec.ts 用 javaScriptEnabled: false 真跑一遍首页并断言标题、两个片段区块、编辑内容都可读。 这比绝大多数「微前端 + SEO」方案都扎实。问题全在发布级的 SEO 表面。

F-08已修复全仓库没有 robots.txt、没有 sitemap，也没有 canonical / OG / hreflang

按文件名搜索 robots* / sitemap* 结果为空；Next 的 robots.ts / sitemap.ts 约定文件也不存在。 7 个页面的 metadata 只有 title + description 两个字段——没有 alternates.canonical、没有 openGraph、没有 twitter card、没有多语言 hreflang。 唯一的结构化数据是 page-product 的一段 JSON-LD。

F-04已修复唯一入口的两处 fetch 既无超时也无取消，而这个位置恰好被审计规则排除

网关的页面反代（/*）和资产反代（/_next/*）都是裸 fetch(...)，没有 AbortController，没有超时。 Node 的 fetch 本身没有默认超时，Fastify 也不加，所以一个卡死的页面进程会让网关请求无限期挂住。

它本该被 audit:deps 的 raw-fetch-in-business-code 规则拦住，但该规则的作用域函数是 /^apps\/page-[^/]+\/(app|src)\// ——apps/shell-gateway 不匹配任何分支，被静默豁免。 最需要这条规则的组件正好是唯一逃过它的组件。

同一问题的另一面在运行时层：@mvp/runtime 的 withTimeout 只是 Promise.race 一个定时器然后返回兜底， 不 abort 底层请求。每请求最多 9 个槽位、每个 200 ms 超时，慢片段场景下在飞请求数没有上限（socket 与未读响应体持续占用）。 对照之下 @mvp/request 反而做对了——它老老实实用了 AbortController。

F-17按要求跳过配置缺失是静默回落，不是 fail-closed

URL 环境变量的校验只在已设置时生效：pageServiceUrl(envVar, fallback, env) 里 override === undefined 直接 return fallback， 而 fallback 是 http://localhost:4101 这类开发默认值。所以「值写错」会在启动时炸（好），「忘记设」会安静地去拨 localhost（坏）。 文档里「typo 会 fail fast 而不是静默拨 localhost 默认值」这句只覆盖了前一半。

资产反代用 pageOriginFromReferer() 从 Referer 的 pathname 反查路由来定位页面 origin，取不到就 404。 任何裁剪/缺失 Referer 的场景（隐私设置、某些代理、跨源导航）都会让 /_next/static/* 404，而这会连带打挂 hydration 和样式。 代码里对这个后果有清楚注释，说明是已知取舍，但它是个脆弱的依赖。

一句话总评

这套仓库的思想密度和工程纪律远高于同类项目——纯计划 + 副作用外壳、全面依赖注入、契约在边界真的 parse、 codegen 消灭漂移、affected 引擎宁可过度构建也不静默少构建、诚实记录每一处取舍。这些不是能靠堆时间补出来的东西。 初版诊断是：问题不在「架构对不对」，而在两端没有收口 —— 入口端（新建单元的脚手架）产出不可运行，出口端（镜像、资源、超时、缓存、SEO 表面）还是 demo 配置。

这一轮把入口端和出口端的代码部分收掉了：脚手架现在产出实测可运行的单元，最小部署单位的交付链路变成一条带退出码的命令， 入口有超时与取消，降级不再泄漏内部拓扑，缓存有界且 tags 可用，SEO 门面补齐，冷克隆不再红， 连门禁自身的三处盲区（docs:test 的豁免、CSS 的空测量、审计的作用域漏洞）也一并修了。净变更 +2478 / −3123—— 删掉的比加上的多，因为 2,718 行样板换成了 940 行。

剩下的是纯运维配置（镜像多阶段、k8s 资源与 HPA/PDB、页面指标、CDN 缓存头、fail-closed env），按约定留给各家自己的部署体系。 以「能否接手」为标准，它现在的位置是：框架本身可以接手了；把它放到生产流量上，还差那一层部署工程。
