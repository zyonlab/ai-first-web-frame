我们自研了什么、别人已经做了什么、该借哪一段

这份报告把系统拆成 8 条能力轴，每条轴找到对应的开源竞品，用拉取到的一手资料（官方文档、GitHub、npm registry） 核实它们的真实功能，再和我们的实现逐项对位：谁做得更好、差在哪、可以借什么、各自的成本是多少。

一句话结论：在片段组合这条主轴上我们和 Podium 各有胜负（它更成熟、我们的调度更强）； 在 affected / 构建门禁这条轴上我们基本是在重造 Nx 的子集且缺了它最值钱的缓存； 在 AI agent 操作面这条轴上没有框架级竞品。 最该立刻借鉴的是 Podium 的 proxy 机制 —— 那是我们结构性缺失的一块。

04

逐轴深入

A · 片段组合与降级 ↔ Podium layout / Tailor 各有胜负

他们怎么做（已核实）：podlet 暴露一份 manifest，字段就七个 —— { name, version, content, fallback, css, js, proxy }。layout 侧 layout.client.register({ name, uri }) 注册，podlet.fetch(ctx) 取内容， res.podiumSend() 输出。client 支持 retries，proxy 支持 timeout。 降级是 podlet 自己声明一个 fallback 路径，layout 在失败时取它。

Tailor（已归档）走的是另一条：<fragment src primary async fallback-src> 标签 + 流式并行， 其中 primary 决定整个响应的状态码 —— 主片段挂了，页面就该返回它的错误码。

我们怎么做：槽位声明在 manifest.slots.json，比 Podium 多出 strategy（四种渲染策略）、cachePolicy、dependsOn、dataDependencies、required。 调度器建 DAG 拓扑分层并行、每槽位独立超时与 abort、失败传播到下游、流式时每个槽位一个 promise 独立 flush。 这套编排能力 Podium 完全没有 —— 它的 layout 就是「注册、取、拼」。

可借鉴 → Tailor 的 primary 语义。我们的 required: true 目前只影响 execution.health，不影响 HTTP 状态码 —— 一个 required 槽位全挂的页面仍然返回 200。 对 SEO 和监控都不理想：爬虫会把降级页当正常内容收录。加一个「required 槽位失败 → 5xx（或 503 + Retry-After）」的可选策略，约 0.5 人日。

B · 片段的后端数据通道 ↔ @podium/proxy 我们结构性缺失

他们怎么做（已核实）：podlet 在 manifest 里声明 proxy: { api: 'http://backend/some/path' }，layout 的 @podium/proxy 自动把它挂到 {pathname}/{prefix}/{podletName}/{proxyName}/，默认超时 6000ms。 于是 podlet 的浏览器侧代码可以请求 /podium-resource/bar/api/ —— 同源、无需 CORS、无需把片段服务地址暴露给浏览器、页面也不需要知道片段的后端在哪。

我们怎么做：没有这一层。片段的服务端渲染可以用 @mvp/request 调后端， 但 island 在浏览器里想拿数据没有标准通道。现状是要么页面把数据注入进 island snapshot（一次性、不能刷新）， 要么 island 自己知道一个后端地址（跨源，并且把内部拓扑暴露给浏览器 —— 这正是我们刚修掉的 F-11 同一类问题）。

C3 spike 的 assetsUrl 已经踩到过这个坑的邻居：跨源 module fetch 必须加 Access-Control-Allow-Origin，而且那是真机浏览器才发现的。代理机制能从根上消掉这类问题。

可借鉴 → 本报告的第一优先级。在 FragmentManifestSchema 加一个 proxy?: Record<string, string>，页面侧按固定前缀挂载转发（Next 的 route handler 或 shell 网关都行）。 带上我们已有的超时/取消和 trace 透传，比 Podium 的版本还能更完整。估 2–3 人日。

C · 请求上下文传播 ↔ @podium/context 各有胜负

他们怎么做（已核实）：七个标准头 —— podium-requested-by、podium-debug、 podium-locale、podium-device-type、podium-mount-origin、 podium-mount-pathname、podium-public-pathname。 关键是可扩展：.register(name, parser) 能追加自定义 parser 进上下文构造流程。

我们怎么做：RequestContextSchema 覆盖 traceId / requestId / locale / tenant / user / session / featureFlags / theme / device / experiment / userAgent / timestamp，整体过 Zod 校验， 并且贯通 trace。维度和严谨度都超过 Podium。

差距：我们的 context 是封闭 schema。业务要加一个维度（比如 A/B 分桶、渠道来源、会员等级）， 必须改 @mvp/contracts —— 而那是框架包，按分层规则业务代码碰不得。Podium 的扩展点让这件事变成本地操作。

可借鉴 → 给 createRequestContext 加一个 extensions?: Record<string, ContextParser>，解析结果放进 ctx.extensions（schema 用 z.record(z.string()) 兜底），随 header 一起序列化给片段。 保住了「框架不认识业务词汇」的分层规则，又给了扩展口。估 1 人日。

D · 注册表、版本与发布 ↔ OpenComponents / Podium 的 version 语义 各有胜负

Podium（已核实）：manifest 里的 version 是缓存失效信号 —— 官方文档原话是 这个值在新版本部署时必须更新，因为 layout「uses this value to know whether to refresh the podlet's manifest and fallback content」。 没有 registry、没有 channel、没有 promote/rollback（未核实：检索未见此类概念，据其设计推测是有意交给基础设施层）。

OpenComponents（已核实）：有真正的 registry 服务 ——「the REST API that stores, versions, and serves components」， oc init / oc dev / oc publish，发布时自动做资产优化和版本管理，语言无关。 这是「跨团队、跨仓库分发」才需要的规格。

我们怎么做：registry/registry.data.json 一个文件 + 四个 CLI。 但有两样他们都没有的：channel（stable/canary/preview）+ promote/rollback 的版本历史， 以及原子写 + 建议锁 + 乐观内容哈希（并发写返回 {"status":"conflict","retry":true}）。 后者是为「多 agent 并行操作同一份注册表」设计的，在人类团队里几乎没人会做到这一步。

判断 → 现阶段不建议上 OC 那种 registry 服务。一个 JSON 文件的好处是它进 git、有 diff、 能被 affected 引擎内容比对从而收窄重建 —— 这恰恰是我们最值钱的性质之一。等到「跨仓库分发片段」成为真需求时再说（估 2–4 人周）。

E · 客户端集成与版本协商 ↔ Module Federation 2.0 他们更强

他们怎么做（已核实）：2.0 相对 Webpack 5 原版新增 Manifest、Federation Runtime、Runtime Plugins System、 Dynamic type prompt、Chrome Devtool。 mf-manifest.json 含 exposes / shared / remotes， remotesInfo 记录所依赖的生产者模块及其 matchedVersion。 运行时已抽成独立 SDK，可以不依赖构建工具动态注册和加载远程模块。

我们怎么做：island 的 C2 握手 —— 片段在 SSR HTML 里内联 {fragment, version, contractHash} 快照，页面 bundle 用 registerIsland(name, comp, { expectedVersion, expectedContractHash, propsSchema }) 声明期望， 不匹配就完全跳过 hydration，保留 SSR HTML 作为最终静态态并告警。

差距很清楚：MF 能协商并加载正确版本；我们只能检测到错位并拒绝。 我们的做法在「不静默出错」上是对的，但用户拿到的是一个不可交互的组件。

可借鉴 → 只有在重启 C3（island 独立部署）时才值得投入。那时 mf-manifest.json 的 remotesInfo.matchedVersion 是现成的设计参考 —— 甚至可以直接用 MF 的运行时 SDK 而不是自研加载器。 估 1–2 人周，且应等到「island 单独上线」真的成为需求（当前决策记录是 no-go）。

F · affected 与门禁 ↔ Nx 他们更强（且我们在重造）

他们怎么做（已核实）：nx affected -t test 只跑受影响项目； project graph 自动推断项目间依赖；targetDefaults + dependsOn（^ 前缀表示依赖项目的同名任务）定义任务管线； 本地缓存 + 远程缓存。边界规则是 @nx/enforce-module-boundaries（ESLint 和 Oxlint 都有）， 项目打 tags，用 depConstraints 的 sourceTag + onlyDependOnLibsWithTags 约束， tag 支持通配符、正则、glob。

我们怎么做：tools/release-tools 1,257 行自研 affected 引擎 + 六个审计 2,101 行。 我们独有的是注册表数据文件的内容 diff 收窄（promote 一个片段只重建它和挂载它的页面）—— Nx 不知道什么是 fragment registry，这条得自己写。

差距：① 没有任务缓存。pnpm verify 每次全量 165 秒，其中 build 占 100 秒； Nx 的缓存能把无关改动的重跑压到几秒。② 分层规则是硬编码在审计代码里的三层，加一层要改 TypeScript； Nx 的 tags/depConstraints 是声明式配置。

可借鉴 → 两条，优先级不同：
(1) 任务缓存 —— 不必迁 Nx，套一层 Turborepo 只用它的缓存与任务图即可，我们的 14 道门禁原样保留。 估 2 人日，收益是日常 verify 从 165s 降到秒级。这是本报告 ROI 第二高的一条。
(2) 声明式边界 —— 把三层硬编码改成 tags + depConstraints 风格的配置。估 2 人日， 收益是加领域/加层不用改审计代码。

G · 延迟 SSR / islands ↔ Astro Server Islands 各有胜负

他们怎么做（已核实）：组件标 server:defer，构建期换成一段小脚本， 运行时向一个特殊 endpoint 请求并换回 HTML；占位用具名 slot="fallback"，随页面一起先渲染、就位后替换。 代价写在文档里：props 以加密字符串放进 URL query， 超过约 2048 字节会转成 POST，而 POST 不被浏览器缓存； 函数不能传，循环引用不支持。

我们怎么做：dynamic-ssr 槽位 + <FragmentSlotStream> + <Suspense>， props 走 POST /render 的 body，没有大小限制；每槽位独立超时、abort、DAG 依赖、fallback。

本质区别：Astro 的 island 是同进程组件（零运维），我们的片段是独立 HTTP 服务（可独立部署，代价是一个服务）。 这是「独立渲染」和「独立部署」的分野，不是谁做得好的问题。

可借鉴 → Astro 把「代价」写进文档正文的做法值得学（2048 字节、POST 不缓存都是明写的）。 我们的 docs/COMPOSITION.md 已经有这个习惯。功能上没有需要抄的。

H · AI agent 操作面 ↔ 无框架级竞品 我们更强

生态现状（已核实）：存在的是分散的约定而非框架能力 —— llms.txt（文档索引约定）、AGENTS.md（仓库级 agent 配置格式）、 MCP（工具暴露协议），以及「CLI-first，MCP-second」这条正在形成共识的设计原则。

可执行文档这件事，TS 侧确实有工具（这一点要修正我此前的说法）： testdocs（把 md 里的 ts 块当 vitest/jest 测试跑）、 typescript-docs-verifier（只验编译不执行）、 mdoctest（Python 写的跨语言工具，能 auto-fix）、 Effect-TS 的 doctest plugin（用 import.meta.vitest fence）。 但它们都是独立工具，没有哪个框架把它做成自己的强制门禁。

我们怎么做：docs:test（445 行）在 pnpm verify 里执行全部 36 份 AGENT.md 的 38 个代码块、0 豁免； @mvp/mcp（537 行）把发现与生命周期包成 agent 可调工具；四个生命周期 CLI 统一 JSON 信封、未知 flag 拒绝、幂等、原子写冲突重试。

可借鉴 → 两条轻量的：
① 补一份 AGENTS.md（正在成为通用约定，和现有 CLAUDE.md 内容大量重合，可以互相引用而非复制）。估 0.5 人日。
② docs:test 的实现可以对照 testdocs 看看有没有更省的路 —— 但我们的版本已经处理了跨块续写、no-run 豁免、per-package 粒度，未必划算换。

自研 vs 采用的成本账

把自研量按「能不能被现成方案覆盖」分三类。行数为本仓库实测（源码，不含测试）。

07

结论

没有一个项目和我们完全对位，但每条轴上都有比我们成熟的东西。三种情形要分开判断：

  • 如果目标是交付一个微前端产品 —— 理性选型是 Podium（服务端组合，活跃、生产验证、多语言片段） + Nx 或 Turborepo（affected 与缓存），能省掉这里相当一部分自研。我们在 A/F 两轴上确实在重造轮子。
  • 如果目标是「AI agent 能安全高速迭代的代码库」 —— 微前端只是载体，真正的产出在 H 轴， 那部分没有现成品可抄，自研是必要的。这也解释了 llms.txt 里那句 「Consumers are AI agents operating the lifecycle CLIs, not humans reading prose」。
  • 无论哪种目标 —— 可借鉴清单的前五条（约 8 人日）都该做。它们不是「向竞品看齐」， 而是补我们自己的洞：一个结构性缺失、一个数量级的迭代效率、一个 SEO 正确性问题、一个分层死结、一组从来没被测过的预算。

最值得记住的一条：Zalando Tailor 在 2022 年底归档，README 里没有推荐继任者。 这条技术路线有人走过完整的生命周期。选择走它之前，值得先想清楚我们和 Tailor 的差别在哪 —— 我的判断是：差别不在片段组合本身（那部分 Tailor 做得不差，甚至也做性能预算）， 而在谁来操作它。
